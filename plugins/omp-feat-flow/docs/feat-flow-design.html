omp-feat-flow v0.2.0 — 零基础开发者实战指南

omp + 可选 cmux + Linear + GitHub PR · 按一个陌生开发者的真实 User Story 从头到尾展开

如果你完全没听过 feat-flow，先记住它解决的三个痛点：日常用 AI 写需求时，模型最容易犯三个毛病——① 需求边界还没问清就急着改代码；② 上下文一压缩或清屏（/clear）就忘掉先前拍板的边界、切片做到哪一片、甚至把旧代码推错分支；③ 没经过真正隔离的独立审查（和必要的安全/性能审计）就把半成品开成 PR。

omp-feat-flow 的核心思路：不靠「祈祷模型记住规则」，而是用一个落盘的确定性状态机（RunKernel）把写权限、阶段流转、人类拍板点（Gate）与远端交付全部收归程序管辖——模型只管探索、出方案和按切片写测试/代码，剩下的流程卡点由插件自动兜底。

怎么读这份指南：第 -1 步先带你拆开盒子看清里面到底装了哪几样东西；第 0～7 步按真实 User Story 时间线走完「第一次配置 → 接单建树 → 对齐 → Gate 1 方案审查与批准 → 串行 TDD 实现 → 上下文满清屏/恢复 → Gate 2 审查交付 → 崩溃断网对账」；第 A、B 章深度拆解隔离架构与 tech-design.html 如何做到既全面又清晰；文末附命令速查与排障表。

-1先拆盒子：omp-feat-flow 内部到底有什么？

在敲任何命令前，先花 1 分钟建立全景心智模型——插件内部由 5 个明确分工的部件协同工作：

内部组件它具体是什么（存在哪）为什么需要它 / 给开发者什么体验
1. 私有内置方法包
MethodPack		 随插件打包在 resources/skills/ 下的 9 个策展方法（grilling、tdd、code-review、domain-modeling、research、prototype、codebase-design、diagnosing-bugs、retro），新建需求时按内容 SHA-256 快照进 <commonDir>/omp-feat-flow/packs/<digest>/ 零前置安装、零斜杠污染：你装完插件就能直接用，不需要另装外部 skill 仓，你的 / 菜单里也绝不会多出一堆重复的 /skill:grill-me 命令；同时每个进行中的需求严格锁定创建时的 methodDigest，插件升级也不会半路篡改旧需求的规则。
2. 两层配置
（个人级 + 仓库级）		 个人级：~/.omp/agent/omp-feat-flow.json
仓库级：<git-common-dir>/omp-feat-flow/project.json（v2 无手算 digest）		 零手写 JSON：首次 /feat-flow-start 弹出原生表单引导填好，所有 worktree 自动共享同一份仓库配置；环境或凭据变化时会做漂移检测。
3. 状态机内核
RunKernel		 每个需求对应一个独立 run，状态原子落盘在 runs/<runId>/state.json + 文件锁 owner + 绑定的 worktree 定位器 <worktreeGitDir>/omp-feat-flow.json 流程位置永不丢失：即便模型压缩上下文、你敲 /clear 或关掉终端明天再来，当前处于哪个阶段、批准了什么范围、做完哪几个切片、有没有挂起的远端操作，全以磁盘+真实 Git 为准。
4. 四个隔离 AI 角色 author（当前主会话）、scout（只读代码库探路子代理）、coldReader（零工具冷读检验员）、reviewer（只读独立代码/安全/性能审计员） 分工制衡防自吹：写代码的看不到审核提示词的宽容借口；冷读员与审查员每次都是全新干净的内存会话（关 MCP/LSP/扩展），只读提交物与完整 diff 补丁。
5. 两道人工闸与进度卡 Gate 1（方案批准 + 必选建单）、Gate 2（交付确认）+ 输入框上方 3 行实时 aboveEditor 状态卡 不用背流程和命令：平时 AI 自动推进；只有到真正需要你拍板的 Gate 时才会停下来弹窗，进度条实时告诉你在哪一步、上下文占了多少、下一步干嘛。

0首次初始化（User Story：新同事第一天装好插件）

场景故事：小王刚装好 omp-feat-flow，打开公司的 my-app 仓库输入 /feat-flow-start。因为是第一次用，他既没有建过个人配置，这个仓库也还没有接过 feat-flow。
0.1 个人级一次性引导（每台机器只需 1 次）

插件弹出一个整洁的原生表单（ui.formDialog；若宿主不支持表单则自动降级为分步选择），小王只需在一个框里确认：
① 角色模型与 thinking effort：分别为 scout（建议快模型+medium）、coldReader（建议快模型+medium）、reviewer（建议强推理模型+high）选好模型；author 默认「跟随当前 /model」，不强抢你在主窗口的临时切模；
② Linear 凭据：选启用后通过掩码输入框粘贴 Key，macOS 下写入 Keychain omp-linear-api-key（非 macOS 明确提示使用环境变量 LINEAR_API_KEY 持久化，绝不把 Key 存进明文 JSON），并自动拉取团队让你预选常用团队；
③ 环境探测与覆盖开关：自动探测 gh auth status 与 cmux 可用性，确认是否显式允许本机全局 skills 覆盖私有方法包（默认关闭，防止被无关全局 skill 静默劫持）。
断点续填与漂移修复：哪怕引导填到一半按 Esc 取消，已完成的步骤已落盘，下次重跑从断点接着填；日后某个模型下线或 Key 失效，再次启动时会主动拦截提示修复。

0.2 仓库级一次性引导（每个仓库只需 1 次）

个人配置保存后，插件立刻对 my-app 发起单次仓库配置表单（存至共享 <git-common-dir>/omp-feat-flow/project.json，之后所有 worktree 通用）：
① 自动推断 origin、owner/repo（不再用假占位符糊弄，解析不出时要求手填合法路径）、本地 prBase 候选（如 staging / main，用本地 refs 零联网秒开）和 worktreeRoot（如 ../my-app-worktrees）；
② 自动扫描仓库内已有域文档（GLOSSARY.md、GLOSSARY-MAP.md、CODING_STANDARDS.md、docs/adr、.claude/rules 等）作为独立审查的知识入口；
③ 选择 Linear 协作模式：required（默认：进实现前必须有单）、optional（允许跳过）或 disabled（纯 GitHub PR），以及交付回写状态（如 In Review / In QA）与建单采集字段（project / milestone / labels / priority / cycle）。
绝不静默降级：若个人开启了 Linear 但当前离线或团队列表为空，插件会明确弹窗确认是否暂改纯 GitHub PR，不会悄悄把配置写成 disabled。

安装方法与升级重设：omp plugin marketplace add darian-deng/agent-plugins && omp plugin install omp-feat-flow（升级后需重启 omp 进程才加载新包，/reload-plugins 不替换已加载代码）；随时跑 /feat-flow-start config（或在无参菜单选配置项）修改配置。

1启动或找回需求：/feat-flow-start

配置就绪后，小王不用记任何分支短名，直接在主仓库输入一句自然语言需求（如 /feat-flow-start 登录超时后自动重试并展示错误提示），或粘贴 Linear 单号/链接（/feat-flow-start DESK-1234），或直接敲 /feat-flow-start 从已有列表点选。

在真正创建分支前，插件会在仓级互斥锁（provisioning.lock）下执行全仓查重（按 Linear 单号 / 已结算建单回执 → 需求摘要 / runId → 分支名 → 目标路径 顺序扫描），并把你的原始需求描述（或从 Linear 拉取的标题与摘要）持久化写入 state.initialTask，确保新工作区第 1 轮自动接续你的目标：

你的输入 / 当前所处位置插件会怎么做你看到的反馈
新需求（任意自然语言描述，或 Linear 单号 / 链接） 若带了 Linear 单号，先校验可读性与团队归属并拉取标题摘要；若为自然语言描述，宿主自动派生合法且冲突自动避让的内部标识符（如 req-9a4f2c1b 或 fix-login-8c12a0）与 feat/<id> 分支、固定起点私密 ref、worktree 目录，并先落盘 state.json（owner: null + initialTask）与 locator，然后按每需求互斥锁安全切出独立运行环境。 • 若开启 cmux：自动创建带人类可读标题与仓库指纹标记的 cmux workspace，并直接以引导语拉起 omp 自动开始对齐，父窗口绝不抢锁；
• 非 cmux：同样不在主仓库父窗口占锁，给出单引号安全转义命令：run req-9a4f2c1b provisioned at ../my-app-worktrees/req-9a4f2c1b; continue with: cd '../my-app-worktrees/req-9a4f2c1b' && omp
需求已存在（哪怕你现在人在主仓库或其他目录） 发现同 Linear 单或同 slug 的已有 run：在 cmux 跨窗口树里查找其工作区，找得到就直接 workspace select 切过去；若工作区被手动关过但 worktree 还在，自动重建工作区并持久化新 workspaceId。 需求 desk-1234 (DESK-1234 · implementation) 已存在于 .../desk-1234，已为你切换到对应 cmux 工作区。
已在需求 worktree 内部执行 /feat-flow-start 认领该 run（支持带参数补绑 Linear 单）。若此前因崩溃留在阻塞态：尚未批准方案时自动 restore；已批准方案但上次异常退出则弹出一次接管确认。 resumed desk-1234; nothing was created.
已有另一个存活 omp 会话正占用此 run 文件锁 owner 被其他活跃进程持有，拒绝双写破坏状态。 This run has an active owner; inspect it without taking over.
完全旁路保证（普通项目零干扰）
在没有初始化 run 的普通 Git 仓库或非 Git 目录中，不管是主会话还是派生子代理（task / /tan），omp-feat-flow 对全部工具（write、edit、bash、task、MCP 等）100% 直接放行。遇到极端情况需要临时跳过门禁时，可设置环境变量 OMP_FEAT_FLOW_OFF=1。

2需求对齐阶段：只读探索、五类边界与自适应分级

场景故事：小王切进了新开的 desk-1234 工作区，进度条显示 ◉ 对齐 ── ○ 方案 ── ○ 实现 ── ○ 交付。他直接和 AI 聊需求：“登录接口超时后现在会静默卡死，帮我加上 5 秒超时和可重试错误提示。”此时所有写代码工具都是关闭状态，AI 不会上来就乱改源码。
  • 只读探路 + scout 子代理放行：AI 可以自由调用 read、grep、glob、lsp 只读查询（hover/definition/references/diagnostics 等），也可以派发只读 scout 子代理（同时兼容单次与批量 tasks[] 调用，自动使用你在引导里为 scout 配置的模型和 effort）大范围摸清相关模块，而不撑爆主会话上下文；任何非 scout 的写代码子代理都会被直接拦截。
  • 五类边界追问（支持直接喂 PRD）：

    goals 目标non-goals 非目标business-boundary 业务边界error-path 错误路径acceptance 验收标准

    AI 基于仓库真实代码，用带推荐答案的提问帮小王拍板未决边界（若小王直接丢来一份带 ## Decisions 的 PRD 文件路径 prdPath，插件会先读出已决条目，只问空白项）。
  • 顺手沉淀术语/架构决策（knowledge 通道）：对话里如果明确了一项团队术语（GLOSSARY.md）或不可逆架构决定（docs/adr/），AI 通过 feat_flow_request 提交单文件知识提案，经冷读校验与小王点击确认后只落盘那一个文档，绝不顺带敞开代码写权。
  • 按规模自适应提交方案（零临时 JSON 文件）：AI 直接内联调用 feat_flow_request 提交 plan（含严格串行切片 slices、行为与测试描述、不变式 invariant）、必填的风险/规模画像 signals、declaredFiles 与结构化技术方案 alignmentDoc（不再允许写入临时 JSON 文件）：
    宿主判定的需求等级判定尺度对齐与审批节奏差异
    Small（快车道）≤3 文件 · 0 风险标记 · ≤1 切片保留 worktree 隔离与测试/CR；允许单次内联直交 plan（宿主自动合成精简边界，或一次合交 boundaries + plan），跳过 LLM 冷读秒开 Gate 1，并支持人工在 Gate 1 勾选受限 autoDeliver。
    Medium≤10 文件 · ≤1 风险标记 · ≤3 切片必须收敛全部 5 类边界 → 生成完整离线 tech-design.html → 后台自动触发全 7 核心节校准冷读 → Gate 1 与 Gate 2 双闸把关。
    Large>10 文件或 ≥2 风险标记或 ≥4 切片或涉及 db-schema / data-migration / payment完整 5 类边界 + 完整 tech-design.html + 全 7 核心节校准冷读 + 批准后主动建议先 /clear + Gate 1 可选开启「中段复核 Checkpoint Gate」与中途 plan.amend 调整剩余切片。

3Gate 1：HTML 技术方案评审、冷读校准与强约束建单

场景故事：方案刚提交，插件就在本机默认浏览器自动为你打开了 tech-design.html（无需额外敲看图命令），同时 AI 总结 4 行要点并停下；对话进入空闲后，Gate 1 自动弹出原生表单（也可随时手动输入 /feat-flow-approve）。
  1. 先看「本次需求专属工作流图」与安全/性能标识： 浏览器自动弹出的 tech-design.html 第一屏就是由宿主按本次真实画像生成的 SVG 流程图与徽章（长流程支持横向平滑滚动）——小王一眼能看清：哪些节点自动跑、哪几步是 HUMAN GATE、以及 Security Review: ON/OFF 和 Performance Review: ON/OFF 为什么开或关。
    通用插件原则（不硬编码仓库私有路径）：插件不会用僵硬的路径规则替你的团队乱猜；signals.riskFlags（auth、crypto、secrets、untrusted-input、network-protocol、ipc、db-schema、data-migration、payment、lockfile-change、permissions、hot-path、memory-sensitive）由模型在提交方案时必填并透明展示，而小王在 Gate 1 的原生 ui.formDialog 里可以直接做人工覆写（强制开启 / 豁免关闭），提交后插件会立即重绘更新 tech-design.html。
  2. 前置校准冷读检验（仅对可变模型内容）： 对于固定不变的宿主审批权限模板，宿主直接做确定性校验（零延迟）；对于 Medium / Large 的模型编写方案正文（AlignmentReadModel）及知识变更 diff，插件在后台派发零工具的 coldReader 会话跑一次严格 JSON 校准冷读（具体如何防漏防废话见 第 B 章），未通过则拒绝进入确认框，明确指出哪一核心节缺失或冗余。
  3. Gate 1 原生表单决策（ui.formDialog）： 在一个交互框里呈现摘要、范围、分级、安全/性能状态、切片清单与 HTML 路径，小王可选择：
    • 批准进入实现（默认流程：做完全部切片后经 Gate 2 人工确认再交付，2 个 Gate）；
    • （仅 Large / ≥4 切片 / 含不确定性活动时出现）执行节奏选择：可保持全程直通 Gate 2，也可勾选在指定中段切片完成后暂停一次 Mid-Checkpoint 复核（含 prototype/research 活动时默认推荐在首片验证后即停下检查）；
    • （仅 Small 且填了精确 declaredFiles 时出现）批准并自动交付：全由人工在 Gate 1 显式授予，且后续如果实改文件超出声明清单、或交付前变基改写了 HEAD，会自动吊销并退回人工 Gate 2；
    • 重新打开 tech-design.html 查看流程图、单独覆写 Security / Performance 独立审计开关，或选暂不批准继续在聊天里调整方案。
  4. linear.mode === "required" 硬门禁建/绑单： 小王如果刚才启动时用的是自然语言描述还没关联 Linear 单，在 Gate 1 真正解锁写权前，插件必须通过 ui.formDialog 引导现场新建（自动预填好你的原始需求标题、已决边界与切片清单，支持选填 project、milestone、labels、priority、cycle，并用 originMarker 幂等防重复建单）或绑定已有单号。未绑单绝不放开写权限！

4实现期（非 Gate）：AI 自动串行 TDD 与宿主实测护栏

场景故事：Gate 1 一通过，进度条立刻变为 ✓ 对齐 ── ✓ 方案 ── ◉ 实现 [1/3] ── ○ 交付。小王不需要一句一句催促「做下一个」，AI 自动按切片顺序推进：写红测 → 最小实现变绿 → 跑验证 → git commit → 报完成 → 自动进入切片 2。
  • 宿主亲自验票（不轻信口头汇报）：AI 每完成一个切片调 feat_flow_request({ sliceUpdate: { status: "done" } }) 时，插件后台强制检查四件事： ① 工作区干净（git status --porcelain 无未提交文件）； ② HEAD 严格位于当前基线之后、匹配传入 SHA 且不与之前切片共用同一个提交； ③ 宿主在本次切片写编辑之后确实在 tool_result 里观测到过非平凡测试/构建/类型检查命令以 exit 0 通过（git commit / echo test 不算数；若仓库本身有 tests/ 或 package.json test 脚本，禁止用 no-tests: 蒙混过关）； ④ 若此前勾选了 Small 级 autoDeliver，顺带预检是否超出 declaredFiles。
  • worktree 文件防火墙 + 命令行/MCP 护栏：
    • 所有 write / edit 以及 knowledge 写入都会先解析 realpath，哪怕通过 ../ 或符号链接指向 worktree 外部也会被立刻拦下（path-outside-worktree）；
    • bash 放开用于本地测试、构建和 git commit，但命令解析器会自动跳过 git -C . / -c 等全局参数，精确拦截任何远端交付行为（git push、gh pr create/merge/edit/close、Linear GraphQL）；
    • 只读查询类 MCP（mcpReadOnlyHint === true，如读 Linear 单、查 PostHog/Notion）正常放行，但会拦截交付类远端写 MCP（如 mcp__linear_save_issue / mcp__linear_save_comment / mcp__linear_merge_diff），确保所有对外交付收敛到 Gate 2。
  • 大型需求中途发现偏差怎么办？（中段复核 + 原子 plan.amend + 实现期 scout）：
    • 实现期继续使用 scout：主会话在实现大型多模块需求时仍可派发只读 scout 子代理跨模块探路，避免把 60% 上下文全耗在读文件上；
    • 中段复核 Gate（checkpoint-review）：若 Gate 1 开启了中段复核，当指定切片标为 done 时，内核会自动挂起 pendingGate 锁住后续写权（即使重启也不会丢失该停顿），展示已完成切片提交、git diff --stat 与途中发现，由你拍板「继续剩余切片」或「停下来调整方案」；
    • 原子改案与无损退回（plan.amend）：若中途踩坑需要拆分/重排剩余切片，AI 提交 plan.amend 后宿主会强制校验「已完成切片的 id/行为/测试/依赖必须原样保留在前缀并继承宿主 commitSha」，把新方案暂存在独立的 pendingAmendment 并自动打开更新后的设计图——批准后原子切换并保留原有的安全/性能强开开关；若你点击退回，原 approvedScope 与原切片计划毫秒级无损恢复，绝不卡死。

5上下文快满了怎么办？（45% / 60% / /clear / compact / 关窗续跑）

场景故事：大需求做到第 2 个切片一半时，模型调用了十几次 read 和 bash，上下文一路涨到 61%。小王以前最怕两件事：要么不清理导致后面模型失忆改坏代码，要么清屏后还得背一串恢复指令重新给 AI 讲一遍背景。v0.2.0 把这一步做成了完全无感接续：
触发场景 / 阈值插件自动做什么开发者只需要做什么
切片之间上下文 ≥ 45%（未到 60%） 每当一个切片刚标记 done 且后面还有待做切片时，不仅提示用户，还会把 ADVISORY 直接写进工具返回结果喂给模型，促成在切片间隙主动 checkpoint 并清屏。 让 AI 存个 checkpoint 后敲 /clear，然后直接说「继续」。下次唤醒时 Recovery Brief 会同时带回原始需求目标与 Gate 1 拍板的核心架构/接口契约/失败模式，跨多轮 /clear 也不失忆。
在 tool_result 采样中立即将状态落盘锁定为 FINALIZING_SLICE（或非实现期 WRAP_UP）：封锁新文件修改，仅允许运行测试、执行本切片的 git commit 并提交 checkpoint（把当前进展、未决问题、真实 gitHead 写入 handoff）。若模型忘了存断点就想停下，session_stop 会拦截并催它补写一次。 看到顶部提示「✓ 断点已保存 · 随时敲 /clear」后，输入 /clear，然后像平常聊天一样打「继续」即可！不需要任何额外恢复命令。
直接 /clear 或自动 compact 只要没有未结算的外部操作且材料摘要完整，同进程 /clear / compact 绝不吊销写权限，仅原子递增 contextEpoch 并清除上下文锁。下一轮对话首条 before_agent_start 自动从磁盘和真实 Git（git log、脏文件、已决边界、切片 [x]/[>]/[ ] 与 handoff）重建一份权威 Recovery Brief 注入系统上下文（也在压缩钩子 session.compacting 同步注入）。 什么多余口令都不用背，直接接着发下一句需求或说「继续」。
正常退出后次日重开窗口
cd <worktree> && omp		 上次干净退出时内核核验 readiness === "ready"、0 未决操作、权限合法后写入 cleanRelease: true。这些 worktree 本就是为该需求专建的——哪怕新开窗口换了全新的 sessionId，只要互斥锁空闲且摘要校验完整，新会话自动继承已批准的实现写权（若退出前正停在 pendingGate 审批点，重开后会自动用新世代重铸门禁令牌继续锁住写权并弹窗，绝不丢失闸门）并首轮注入 Recovery Brief。 进入对应 worktree 启动 omp 直接继续工作（若发现上次未干净退出/崩溃或有未决操作，则会严格锁住并先要求对账/确认，绝不盲目放行）。
防洗白安全底线：如果一个未获授权的陌生会话在阻塞态（owner-recovery / owner-authorization-required）打开 run 后正常退出，dispose({ clean: true }) 绝不会为它写入 cleanRelease: true，彻底杜绝通过「进门退出再进门」绕过人工授权。

6Gate 2：独立代码/安全/性能审查与事务化幂等交付

场景故事：最后一个切片完成并干净提交后，AI 核验工作区干净并调用 readyForDelivery，Gate 2 确认框弹出（仅当 Small 级在 Gate 1 经人工勾选自动交付、且此刻终态 HEAD 经宿主二次复核干净、全切片完成、测试通过且改动 100% 落在 declaredFiles 内时才会直通交付）。
  1. 准入硬核验与前置预检：不管是弹出 Gate 2 确认还是开发者直接敲 /feat-flow-finish，插件首先校验：若有计划则全部切片必须为 done、工作区必须干净、且前置条件（github.repository、linear.mode === "required" 的单号与凭据）完备——所有预检都在状态机切入 delivery 之前完成，避免缺配置时把 run 卡死在不可编辑的交付态。
  2. 先 Sync 再封存 Diff 派审（含设计契约对照）：先把最新远端 prBase 变基进来（若基线前进，旧基线上的审查 proof 会立刻失效；若启用了 autoDeliver 且变基改写了 HEAD，自动吊销直通并退回人工验证确认）。随后把完整差异封存到 materials/review-<head12>.patch，派发完全隔离的 reviewer 会话（注入经 realpath 校验 containment 后的项目词汇表、规范文档，以及批准方案中的 Goals / Non-Goals / Contracts / Failure Modes 与完整变动文件清单）执行严格 JSON 规范+规格双轴评审。若 Gate 1 开启了 Security Review 或 Performance Review，同步执行独立的阻塞级安全/性能审计。任何拒绝或格式违规均无损留在 implementation 阶段，修改提交后再重跑 /feat-flow-finish 即可。
  3. 锁定旧 Tip 的四步幂等交付事务：进入 delivery 后，台账先持久钉死首次观测到的远端分支旧 tip（expectedRemoteTip），再按 push → pr → linearState → linearComment 分步落地回执（任一步持久化失败立即中止而不盲目推进下一外部副作用）：
    • 开且仅开 1 个同仓 PR：在证明 remoteSha === HEAD 后按同仓（!isCrossRepository）+ 分支 + prBase + OPEN 匹配现有 PR（免受 GitHub headRefOid 短暂索引延迟导致重复建 PR 的坑）；
    • 回写 Linear（绝不踩坏人工描述）：把单据流转至配置的 reviewState（如 In Review / In QA），并检查最近 50 条评论是否已有本 run 的精确标记，没有才追加一条附带 PR 链接的幂等评论——绝不覆盖人类编辑过的 issue.description！
    delivered desk-1234: PR #7511 (https://github.com/org/repo/pull/7511); Linear DESK-1234 In QA. PR, branch and worktree remain intact.
  4. 展示回执后的安全收尾：先让你看到完整 PR URL 和 Linear 状态，再弹窗询问是否关闭本次 run 自建的 cmux 工作区（点关闭前先把 workspace: null 与 cleanRelease 落盘，防止关闭自身 PTY 导致状态写丢；你手动开的窗格绝不误关）。也可留着工作区跑一次 retro 把这次踩过的坑沉淀成团队 lint/规范，等 PR 合入后再自行删 worktree 和分支。

7断网、Rebase 冲突与崩溃对账（绝不重头来过）

不管遇到中途掉网、Git 变基冲突还是电脑休眠断电，状态机靠外部真实状态自动对账接续：

Alignment 期崩溃或 Linear 建单丢响应

• 未批准方案前异常中断：重新进入目录执行 /feat-flow-start，确认无未决操作后自动 restore 恢复；
• Gate 1 创建 Linear 单时如果断网响应丢失导致 linear-issue 处于 unknown：下次执行 /feat-flow-approve 时会在准入检查之前优先按 originMarker（含已归档检索）查回单据并原子补绑，不会卡死闸门。

Sync 变基冲突 / 断头台重启

若 /feat-flow-sync 遇冲突停在 rebase-merge：台账会保持 git-sync 为 unknown（锁住写入），哪怕你中途重启了 omp，inspectRepository 仍能从 rebase-merge/head-name 认出原本的 feature 分支，不会失去定位；待你手工解决冲突并 git rebase --continue（或 --abort 回退到保存的 preSyncHead）后，再跑 /feat-flow-sync 自动对照 Git 真实历史结算续跑。

交付链路半途断网（例如 Push 成功但开 PR 或写 Linear 超时）

台账已持久化记录 push / pr / linearState / linearComment 的每步状态与 expectedRemoteTip：重跑 /feat-flow-finish 时会自动跳过重复 sync（避免改写已推送的 HEAD），命中已推送则不重推，命中已开好的同仓 OPEN PR 则直接复用，命中 Linear 幂等评论则不再重复回写；若整体已结算完成，重跑会直接返回幂等收据而不重复执行外部写。

B揭秘：方案评审 HTML（tech-design.html）如何保障「全面、清晰、又易读」？

AI 时代最危险的审批反模式，是 AI 在聊天里把复杂方案一笔带过，或者直接吐出几千行原始代码/废话让人类「盲签」。omp-feat-flow 通过五层确定性工程设计解决这一矛盾：

  1. 单一结构化数据源 → 双投影分离（人看 HTML，冷读员只看纯文本投影）：
    模型提交的不是一段自由发挥的 Markdown，而是受严格 Zod Schema 约束的结构化 AlignmentDocument（见 src/profile.ts）。宿主程序由此一次性生成两个受 candidateDigest 绑定的投影（见 src/tech-design.ts）：
    • 给人类看的 tech-design.html：带高对比度徽章、离线内联 SVG 图表、差异表与折叠区块；
    • 给 coldReader 看的 AlignmentReadModel：彻底剥离 HTML/CSS/SVG 语法噪音，按 core（核心）与 appendix（附录）整理成纯文本章节，让冷读员检验的是「信息自洽性」而不是在读 HTML 标签。
  2. 首屏第一眼：宿主程序亲自画出「本次真实流程地图」，绝不让 AI 凭记忆编造：
    tech-design.html 的最顶部（TL;DR + 第 1 节 Workflow Map）不由 AI 自由填写，而是宿主根据实际 RequirementProfile 与 project.json 确定性绘制的 SVG 流程图与徽章——清清楚楚标明本次是 SMALL / MEDIUM / LARGE、哪些步骤 AUTO 自动跑、哪些是 HUMAN GATE、Security Review 与 Performance Review 各自是 ON 还是 OFF 及原因、以及是否启用了 Small 级 Auto-Deliver。人类签字前第一秒就能纠正「小改动误触高风险」或「高危改动漏了审计」。
  3. 渐进式披露（核心决策默认全展开，庞杂明细收进附录折叠）：
    遵循「不点开附录就能拍板核心决策」的信息分层原则：
    • 默认全展开的核心 7 节（core）：① 30 秒对齐摘要（TL;DR + Problem）→ ② 本次专属工作流图 → ③ Goals & Non-Goals → ④ 架构落位（含防穿盒避让弧线的 SVG 组件关系图 + 上下游流向与约束）→ ⑤ 机制与失败契约（含接口契约、失败模式与持久化/迁移影响）→ ⑥ 代码改动面清单（逐文件 add / modify / delete，没涉及的动作会明确生成 (none) 占位行，防 AI 悄悄省略）→ ⑦ 串行切片与验收方式；
    • <details> 默认折叠附录（appendix）：长篇的「备选方案淘汰台账（Decision Ledger）」与「风险/假设明细」收进折叠栏，避免首屏视觉过载，需要深究时点开即看。
  4. 零外部依赖离线可用（不用装 mmdc / 无外网脚本 / 无 XSS 风险）：
    全部图表由宿主的 TypeScript 渲染器直接转义输出为原生内联 SVG（支持长标题自动换行、跨节点弧线避让箭头与横向滚动容器），不依赖 mermaid-cli、Chromium 或任何 CDN，在内网/离线环境生成即自动在默认浏览器毫秒级打开；同时与任何自动批准隔离——HTML 永远只是只读视图，最终拍板只能回到终端原生 ui.formDialog。
  5. 反事实 + 消融实验驱动的「全 7 节逐字冷读门禁」：
    为了防止冷读员变成「读两行就喊 PASS 的橡皮图章」，src/questions.ts 执行三道硬防线：
    • 防空洞糊弄（反事实MISSING）：冷读员必须站在「没有对话历史、没有仓库工具的新入职开发者」视角，判定是否存在两种合理理解会导致截然不同的审批或实现结果；
    • 防长文注水（消融测试BLOAT）：要求冷读员做消融论证——如果删掉某段引用后所有核心答案、风险与导航都不受影响，即判 FAIL_BLOAT 退回瘦身；
    • 宿主机逐字原文核验：返回必须满足严格 JSON Schema，必须同时覆盖全部 7 个核心 sectionId（tldr、workflow、goals、placement、mechanism、change-surface、verification），且每条回答引用的 quote 必须在对应章节原文中逐字存在，否则宿主直接报错拦截！
