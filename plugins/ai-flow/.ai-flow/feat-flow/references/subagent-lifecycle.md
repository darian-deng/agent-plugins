# 子代理生命周期：谁可以等、通知怎么读、失联怎么救

> **触发**（撞上任意一条就读本文件）：要 dispatch 一个执行单元；收到宿主的「完成」通知、准备落盘 / 评审 / 派下一个单元；`/clear` 之后回到 stage-4；某个子代理迟迟没回报。
> 读者是主 session。本文件里的实测数字**全部来自 grill-flow 的运行记录**（同一个宿主、同一套 `Agent` 工具，机制通用；feat-flow 自己没有对应量级的采样）——引用时照这个口径说，别把它们说成 feat-flow 的实测。

## 一、谁可以等：这条决定了怎么派、怎么等

**只有能被唤醒的执行体才可以等待。**

- **主 session 可以等**：它派出去的子代理、丢后台的命令完成后，宿主会把它唤醒并把完整回报投递进来（grill-flow 实测同一份记录里 4 次，从入队到唤醒 3 毫秒）。
- **子代理不能等**：它一旦结束回合就是**终止**——这个宿主里子代理没有「挂起」态。它把命令丢后台之后无事可做、只能结束回合，于是自杀；宿主随即给你发一条 `completed`，正文是它最后那句「在等 X」，读起来像「还在跑」。grill-flow 实测这个形态在一次运行里出现 **8 次以上**，最长一次空转 **1 小时 07 分**。

### 主 session 的「等」长什么样

**结束回合是免费的，而且是最快的那条通道。** 全局纪律「派出去的代理还没全部回来就不给结论」管的是**下结论**，不是**结束回合**。

把它读成「必须保持在场」的代价（grill-flow 实测）：主 session 连发 **671 次 `sleep 1`**（description 全是「占位等待」），占它全部工具调用的 **73%**、输入 token 的 **74.3%**（233.1M / 313.5M），而会话末尾每一次这样的空转都要重读约 **65 万**缓存 token。

**stage-4 是串行的**——你派出一个实施子代理之后，手上没有任何不依赖它结果的活（下一个单元必须等它 commit 完才能派，这是「钉死串行」那条红线要求的）。所以这里的正确形状只有一个：

> ⛔ **dispatch 之后直接结束回合，一个字都不用发。** 子代理完成时宿主会把你唤醒并投递回报，那一轮再落盘 / 评审 / 派下一个。

- ⛔ **不要用前台 `sleep` 占位等待**，也不要用 `until [ -f … ]; do sleep 10; done` 这类轮询循环绕过。前台单条 `sleep N`（N ≳ 22 秒）会被宿主直接拦掉（报错原文 `Blocked: sleep N …`），而循环体里的 `sleep` 不被拦——**别把它当绕过口**：它把一条免费通道换成了「每轮按当时全部上下文全额计费」的收费通道，纯亏。
- ⛔ **不要为「只跑验证」派子代理**（重跑一条 verify、取一个测试计数、复跑某条命令这类）。派子代理的收益是省 context，而这类任务的输出只有几行数字、几乎不费 context，却把工作放到了唯一不能等待的一侧——净亏。**这类活你自己跑**；单条命令超时就丢后台（`run_in_background: true`），它完成时同样会唤醒你。

## 二、收到「完成」通知之后、落盘 / 评审 / 派下一个之前

**完成通知不等于那个子代理已经停了。** 宿主在 agent「这一轮结束且没有存活的后台子进程」时就发通知，而它可以再被唤醒继续跑——feat-flow 的实施子代理在 `verify` 通过之后还有一段活（`assess-candidate` 知识沉淀、注释自查），那段里它仍可能改文件。

**先做一次机械判定，再读正文。** 回报首行必须是 `impl-done: <commit sha>`（耦合簇：该簇最后一个 task 的 sha）。首行不是这个 → **这一票没交付**，不管宿主写的 `<status>` 是不是 `completed`（宿主对「干完了」和「停下了」发的是同一种通知，正文才是差别，而正文很容易被读成相反的意思——grill-flow 实测「Waiting for the full test suite」被读成「它还在跑」，然后等了 1 小时 07 分）。首行判据是唯一不需要理解正文的判据，**先跑它**。

**再核这两条物理信号，都对上才动**（落盘、派评审、派下一个单元）：

```sh
git log --oneline -1          # 必须等于它回报首行那个 sha
git status --porcelain        # 只该剩 docs/feat-flows/** 与本 flow 无关的既有改动
```

`git status` 里出现**本 task 范围内的代码文件仍未提交** → 它还没停（或它没做完就报了完成）。⛔ **这时不要派下一个单元**：feat-flow 全程跑在**同一棵主工作树**上（不像按票开工作树的 flow 有物理隔离），两个实施子代理同时在这棵树上写，后果是 commit 归属错乱——下一个 task 的子代理 `git add -A` 会把上一个的残留一并提交进自己那笔，于是「一 task 一 commit」不变量破裂，而上一个 task report 里记的 sha 不含那部分改动，评审 `git show <那个 sha>` 永远看不到它。

对不上就是它还没停——等（结束回合），或者用 SendMessage 问它，**不要动**。

## 三、`/clear` 重入：先确认在飞子代理死没死

⚠️ **`/clear` 不会杀掉在飞子代理。** grill-flow 实测：`/clear` 之后原子代理仍然跑完并回报，而主 session 已经为同一票另派了一个，于是两个 agent 同时写一棵树（一边提交、一边 `git reset` 撤回继续跑，来回三轮）。feat-flow 没有工作树隔离，撞上时两个子代理写的是**同一棵主树**。

所以重入时，在为任何未 `[x]` 的 task 派子代理**之前**：

1. **看宿主的任务列表**里还有没有活着的 agent。有 → 用 SendMessage 问它进度，别派新的（它带着全部上下文，重派等于让新代理从头读一遍）。
2. **宿主没给你列任务的工具时**（很常见，别因此卡住）：判据退回两条不依赖它自我报告的物理信号——`git status --porcelain` 是否**还在变化**（隔几分钟看两次），以及一条 SendMessage 探针有没有回应。
3. **`git status --porcelain` 有本 flow 范围内的代码改动、而该 task 没有 commit** → 就是上一轮那个子代理留下的中间态。⛔ **不许直接派新子代理进去**：先按入场 Step 0 的工作树守卫停下问开发者（「是上次 task 执行中途崩溃的残留，还是有子代理仍在跑？」）。定夺之后（reset 重来 / 在现状上续）把决定**写进续派 prompt**。
4. **不确定原代理死没死就必须续派时**：在 prompt 里写死「可能有另一个 agent 仍在这棵工作树上，发现工作树被别人改动时停下回报，**不要对抗性地 `git reset` / `git checkout` 掉已有改动**」。

## 四、派给子代理的地板范围与超时

- ⛔ **不给子代理下「整仓全量」的地板要求。** 整仓全量测试超出前台单条命令的超时上限，唯一出路是丢后台，而丢后台 = 逼它自杀（§一）。子代理的验证范围是**该 task 的 `verify` + 本 task 直接影响到的包 / 目录的测试**；**整仓全量回归是 stage-5 环节 A 由主 session 跑的**——那一次跑在全部 task 组装后的树上，才是回归真正该测的对象，而且一轮只跑一次，不是每 task 各跑一遍。
- **要求它给长跑命令设超时**。优先用宿主 `Bash` 工具自带的 timeout 参数；用 shell 的 `timeout 900 …` 之前先确认它存在（**macOS 默认没有 `timeout(1)`**，需 coreutils 或 `gtimeout`——不确认就照抄会拿到 exit 127，最坏被当成测试失败去改代码）。
- **要求它只回门禁命令的摘要**（失败条目 + 末尾几十行），不要贴整段输出：贴进来的整段此后每一轮都重新计费。
- **它等不到就报「受阻」**，第一句说清卡在哪、工作树里现在有什么——这比它自杀之后留一句「在等 X」有用得多。
