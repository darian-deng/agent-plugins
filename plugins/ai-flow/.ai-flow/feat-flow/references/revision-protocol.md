# 前置产物修订协议

中后期 stage 发现「前面已对齐的东西需要改」时，统一走本协议。两个触发入口，汇入同一套影响评估与兜底。

## 触发入口

### 入口 A — 开发者异议

开发者对 AI 当前 stage 产出提出异议。**先判异议是否成立，不反射性接受**（"You're absolutely right"、立即改、表演性同意都是失败模式）：

| 类型 | 描述 | 处理 |
|------|------|------|
| A 事实约束 | 开发者指出 AI 没考虑的事实约束（如「项目已废弃 X 模式」） | 接受 |
| B 纯偏好 | 给不同写法但没理由 | 不接受。要求给真实考量（时间约束 / 历史经验 / 已知风险）；「感觉更好」类无信息量回应不收 |
| C 冲突已有决策 | 与已记录决策冲突 | 逐项过，确认成立后 → 进「影响评估」 |
| D 推翻前置结论 | 推翻前置 stage 已对齐结论 | 进「影响评估」 |

异议成立且触及上游 → 进「影响评估」。

### 入口 B — AI 自查

AI（主 session 或 subagent）自查发现前置 stage 产物漏写 / 错了。直接进「影响评估」。**禁止 AI 自判后默默改。**

## 影响评估（核心，两入口共用）

### 1. 分级

| 等级 | 触发 | 应对 |
|------|------|------|
| **L1** | 推翻已对齐的核心决策 / AC / 范围 | **stop**，向开发者呈现问题 + 建议 abort，并给出理由；确认后重 `feat-flow start`。L1 在日常开发常见且代价高，必须严肃对待，不许硬推 |
| **L2** | 漏写一个约束 / 集成点 / AC 子项，不推翻已有决策 | 暂停当前 stage，回改对应上游文档，开发者确认后再继续 |
| **L3** | 局部命名 / 排版 / 单条 AC 措辞 / 显然遗漏注释 | inline 修为当前态；改了什么按下方「暴露纪律」当场告知开发者，**不嵌进产物正文** |

### 2. 上游产物影响回溯（关键）

**按当前 stage，逐一审视全部已产出的上游产物，不止 design.md。** 当前在 stage-N，受影响的可能包括：

- design.md（决策记录 / 范围 / AC / UI 状态清单）
- architecture.md（N≥2）
- plan.md（N≥3）
- 已 ship 代码 + task-reports.md（N≥4）
- review.md（N≥5）

逐一判断是否受影响，受影响的**全部同步更新**。绝不允许「上游文档停留旧决策、当前产出已是新决策」的分裂状态——/clear 后任何 subagent 会拿到分裂的 source of truth，做出不一致实现。

**回改一律覆盖为当前态**：把上游产物正文改成新决策即可，**不在 design.md / architecture.md 正文里留「原本…改成…/反转…」的演化叙事**——产物正文恒为当前态，修订回溯交给 `git diff`。本协议的「暴露」指当场告知开发者（gate 审查清单 / task report `前置修订` 段，均为一次性沟通），不等于把历史写进产物正文。

### 3. 下游兜底（改了上游后，已完成的下游也要跟上）

- **在 stage-4 触发**：L2 改了 design.md / architecture.md → grep 已完成 task（plan.md 里 `[x]`）的改动文件，评估是否需追加 fix-up task 到 plan.md 末尾（如 `### Task X.5 (fix-up)：补 i18n 接驳`），走标准 SDD 流程。不允许「悄悄改文档但不修已 ship 代码」。
- **在 stage-5 触发**：改文档通常意味着代码也要改 → 把对应代码改动纳入当前 review 循环，重跑自动化检查 + 重派对应 lens reviewer 做验证。

### 4. 暴露纪律

- **L1 / L2 必须停在当前位置等开发者确认**，禁止继续推进当前 stage。
- **L3 禁止默默改**，必须在两个时机之一主动暴露：当前 stage Gate 前的审查清单里加一段「⚠️ 检测到 L3 前置问题：<描述>，已按 <动作> 处理」；或无 Gate 的 stage（如 stage-4 实施期间）通过 task report 的 `前置修订` 段暴露。

## 实例对照

| 场景 | 等级 |
|------|------|
| stage-4 发现 design.md「用 IndexedDB」与 architecture.md 集成点冲突、二者不能共存 | L1 |
| stage-4 发现 architecture.md 漏了一个集成点（如 i18n 接驳），不推翻已有架构 | L2 |
| stage-5 发现 design.md「不在范围内」漏了一个约束（"不支持 IE" 漏写） | L2 |
| stage-3 起草时发现某条 AC 标了 [auto] 实际只能 [manual] | L3 |
| stage-5 发现一处注释拼写错误 | L3 |

## 入口冲突兜底

若 AI 报 L2、开发者认为是 L1（或反之），按入口 A 的「C / D」逐项过，先更新上游再继续。最多两轮仍不一致 → stop 让开发者拍板 abort 还是接受。
