# Stage 1：需求确认

> feat-flow 第 1/6 步 · [流程总览](../helper.md)
> 当前 stage 目的：把模糊需求转成结构化的 design.md，含可测量 AC、UI 状态清单、决策记录、项目命令
>
> **元规则**：禁止 git commit，stage-4 起点统一提交。

## 目标

通过接地式分层拆解 + feat-flow 专属探测，产出一份足够 subagent 在后续 stage 独立执行的 `design.md`。Stage 1 出错下游全废，**信息完整 > 速度**。

## 入场动作（按顺序，主 session 执行）

1. **需求源记录**
   - 引擎注入的「需求」可能只是一句话，也可能指向一份 PRD 文件 / URL / 飞书文档
   - 把来源（路径 / URL / 链接）记到 design.md「外部参考」节，确保 /clear 后仍能回溯
   - 其内容在接地时完整读取（本地 Read / URL→tavily-extract / 飞书→lark-doc），此处不重复读取

2. **ADR 查阅**
   - 执行 `{{flow_root}}/references/adr-scan.md`

3. **项目命令探测**
   - 读 `package.json` scripts / `pyproject.toml` / `Makefile` 等
   - 提取：单元测试 / 集成测试 / Lint / Typecheck 命令，写到 design.md「项目命令」节
   - **落盘前规范成非交互单次运行形式**：这些命令后续全由无 TTY、无人值守的子代理执行（stage-3 verify / stage-4 实施 / stage-5 回归），默认进 watch / 交互、不自行退出的命令会挂死子代理。按 runner 改成跑完即退、以退出码收尾——`vitest` 默认 watch 且非 TTY 也不退，须写成 `vitest run`（或加 `--run`）；`jest` 默认单次运行无需改，watch 才需 `--watch`。改命令本身、不靠全局塞 `CI=1`（部分项目 CI 下行为不同，验证结果会与本地不一致）。脚本名（如 `pnpm test:unit`）按它实际展开的底层命令判断，必要时规范脚本对应的命令
   - 检测不到 → 明确询问开发者，**禁止凭推测填**
   - 不查 pre-commit hook（项目级基建职责，不归 feat-flow 管）

4. **TDD 基建检测**
   - 查项目是否有测试框架 + 测试目录
   - 已有完整基建 → 记到 design.md 决策记录「TDD 基建：已有 [vitest/jest/...]」
   - 无 / 部分 → 此处不自动决定，留到下方强制必问项确认（见下）

## 接地式问询（产出 design.md）

把模糊需求拆成 design.md，逐条对齐**增量写入**、不攒到最后。

**接地优先**：提任何问题前先查——grep/read 现有代码与约束、完整读需求源（本地 Read / URL→tavily-extract / 飞书→lark-doc）、外部选型查官方文档或 `tvly search`。**能查清的不问**；仅凭训练印象的事实 / 技术选项禁止呈现。每条 finding 带可核验来源（`代码 file:line` / `文档 出处` / `tvly/官方`），给不出来源的删掉或降级为 ⚠ 假设。

**增量交错呈现（硬性）**：把现状理解按相关性切成**簇**，**每接清一簇就地呈现该簇 finding + 就地确认/拍板该簇的 load-bearing 结论，再进下一簇**。禁止「把全部 finding 一次性砌成长墙、再把决策攒到最后批量一次问完」——那是让开发者被动阅读、对齐感缺失的根源。

**每个待定点归一类**：
- **finding**（代码 / 文档 / 资料能定）：陈述不问、带来源，仅在决策相关 / 可争议 / 带风险时呈现，其余静默记录。
- **问开发者**（只有他知道：意图 / 取舍 / 优先级 / 业务规则 / 未来计划）：走下方「load-bearing 结论」。
- **⚠ 假设**（接不了地、开发者也拍不了）：默认值 + why + 猜错后果，不卡住、继续走。
- 分不清问谁 → 按时态裁决：能陈述「现在是什么」的先查当 finding，只有「将来应该是什么」才问。

**load-bearing 结论 → AskUserQuestion（成簇增量、单次至多 4 个相关项，带开发者 grill 到清楚）**：
load-bearing 结论 = 塑造本 feature 怎么做、AI 读错则下游设计就跟着错的判定——含**塑造架构 / 行为 / 数据、有持久后果、难回退、有真分叉**的决策，**也含 AI 接地后判定「已锁定 / 上游 master 已定」而本想静默带过、但实质约束本次 feature 的结论**（这类判定本身是会出错的假设——master 与实现常有偏差——最该让开发者拦）。**「已锁定 / 上游已定」类升 load-bearing 的二值判据（防扩张）**：仅当「读错该结论会让下游某 task 做错」或「master 与当前实现存在可指出的具体偏差风险」时才弹；读对了也只是确认现状、无下游后果的，不弹、静默写决策记录。每个 load-bearing 结论都弹 AskUserQuestion 让开发者知情并能拦：
- **选项 1 = 接地后的推荐**，带「为何 + 来源」。给推荐前自检：是否过度建设？有无更小做法？取更小的那个。
- **无真分叉时单选项也要弹**——让开发者看到「AI 准备这么干」并有机会拦，不要因为「没得选」就静默带过。
- **同簇合并（防刷屏）**：同一簇内多个无分叉 load-bearing 结论**合并进该簇的一次 AskUserQuestion**（并列多个待确认项，至多 4 个），**不得逐条各自单弹**；单选项独立弹窗仅用于该簇只剩这一条 load-bearing 结论时。
- 有真分叉 → 补**真实**备选（各标代码现状代价）；**禁止为凑数编无营养假选项**。
- **永远带一项**：「我不确定，你需要为此单独探索代码后给我更多输入以保障我对这块是可以决策的」——此项兜底**已判 load-bearing、但接地后仍有残余不确定**的结论（能自己查清的先查，别拿它替代探索）。开发者选它 → 先在 design.md 决策记录写一条 `<决策点>：待定（开发者要求再探索 X）` 占位（防 /clear 丢失），再定向再探索代码、带更多接地结论重弹此问，拍定后覆盖占位。
- （Claude Code 自动附 Other 自由输入。）
- 每拍定一条**立即写 design.md 决策记录**。分流：**代码已定且改它低影响 → grounded-trivial，记入决策记录、不弹窗；代码已定但后果重 / 难回退 → 仍按 load-bearing 弹窗（选项 1 即接地推荐）**。

**阈值（防刷屏、防静默两头）**：load-bearing 才弹；纯机械 finding（表有某列、某函数在哪、零设计后果）静默写入 design.md、不弹。判不准时按时态裁决——能陈述「现在是什么」的先查清当 finding，只有「将来应该是什么」才问。

**说人话（输出对象纪律）**：读者是**没探索过本仓库、不熟领域黑话的开发者**。呈现给他的 finding / 问题 / 小结，两类词首次出现 ≤1 句展开：①本仓库自造词；②非通用领域缩写 / 模式（如 LWW＝按时间戳取最后写入、outbox＝发件箱、tombstone＝墓碑标记）。通用词（HTTP/SQL）不展开。正文首次出现给 ≤1 句简释，完整权威定义放 design.md「术语表」，冲突时以术语表为准。

**轻量出口**：改动局限已知一两处、无设计决策 → 直接接地确认那一两处，跳过决策树，别把小改撑成仪式。
**范围外想法**（「顺便做个 X」）→ 记入 design.md「暂缓清单」，拉回当前需求。

> 验收标准每条必须可测量，标 `[auto]` 命令或 `[manual]` 步骤，写入 design.md「验收标准」节。

**feat-flow 专属追加：**

**强制必问项**（必须问到并记录，按上「load-bearing 结论」走 AskUserQuestion）：
- TDD 基建「无 / 部分」时：本次 feature 是否顺带建立？
- 触及数据存储 / 线上行为时：数据迁移与回滚 / 灰度方式。

**强制必析项 — 产品安全**：本方案 / 产品设计是否存在漏洞（权限绕过、数据泄露、状态滥用、输入未校验、边界被利用）？主动思考，结论 / 缓解措施记入 design.md；若缓解方案有取舍 → 按「load-bearing 结论」走 AskUserQuestion。

**外部技术调研**：外部选型 / 易变接口必须查证；**隔离调研上下文**——优先 dispatch 独立调研 subagent（general-purpose 或 tavily skill），不在主 session 内联查，保持主 session context 干净。

**ADR 草稿**：关键决策（影响下游多个 stage、难以反转）被开发者拒绝，或反复争论未达成一致 → 当场提议 ADR 草稿写到 design.md「ADR 候选」节（供 Stage 6 兜底再次评估）。

## UI 设计来源对齐（若需求涉及 UI）

涉及任何 UI 改动（新页面、新组件、视觉调整）**必须读 `{{flow_root}}/references/ui-protocol.md` 并逐步执行**：六类状态维度逐项 gap closure、每项未覆盖独立代码探索找现有复用组件、复用组件需开发者显式确认沿用。

## 独立审计（写完 design.md 后必做）

dispatch 一个 fresh subagent（general-purpose 类型）对 design.md 做独立审计——自查有盲区，必须用独立上下文。传入 design.md 全文 + 下列 rubric：

- placeholder 扫描（TBD / 待定 / `<具体值>` 等）
- 内部矛盾或前后不一致
- 范围漂移（讨论中超出原需求的内容混入）
- 每条 AC 是否能写成自动化测试或具体验证步骤
- design.md 信息是否足够下游 subagent 独立执行（不依赖本 session 对话历史）
- 产品安全：方案设计 / 产品设计是否存在安全漏洞（权限、数据暴露、状态滥用、边界条件）
- 术语：自造词 / 领域缩写首次出现是否已展开、是否已收入术语表（面向没探索过仓库的读者）

处理审计结论：
- 审计指出问题 → 主 session 修正 design.md → 让审计员**再自审**一轮
- 审计员与主 session 对某条结论分歧、无法当场达成一致 → **不私下消化**，列入 Gate 审批清单亮给开发者决定（design.md 已记录哪些是开发者决策项，分歧本就该回到开发者）

不做 stage-5 那种多轮独立复核——Gate 即人类升级点。

## 前置产物修订（开发者异议 / AI 自查）

详见 `{{flow_root}}/references/revision-protocol.md`。开发者对产出有异议走入口 A，AI 自查发现前置漏 / 错走入口 B；均先评估对全部上游产物的影响并分级 L1/L2/L3，不反射性接受、不私下消化。

## 输出规格

文件 → `{{project_root}}/docs/feat-flows/<flow_id>/design.md`

`flow_id` 是引擎在 start 时生成的唯一标识，AI 看到 context 顶部注入的实际值（形如 `2026-05-21-x7k3`）。直接用此值作为 docs 文件夹名，**不要自己重新拼日期或加描述性后缀**。

design.md 骨架：

```markdown
# <需求简名>

## 需求
（不限字数）

### 不在范围内

## 约束

## 外部参考
（开发者提供的链接 / PRD 路径 / 飞书文档 + 一句话用途；无则写"无"）

## 术语表
> 本仓库自造词 + 非通用领域缩写的权威定义（首次在正文出现处可简，定义以此处为准）；无则写"无"。
| 术语 | 含义 |
|------|------|

## 项目命令
> 命令须为非交互单次运行形式（跑完即以退出码退出）——后续由无 TTY 子代理执行，watch / 交互模式会挂死。
> ⛔ **「单元测试（限定范围）」必须填**：stage-4 的实施子代理按它跑本 task 范围的测试，那边禁止现编参数（猜错的 filter 零匹配也退出 0 = 假绿）。限定不了就写"无"，stage-4 据此退回跑整条。
| 用途 | 命令 |
|------|------|
| 单元测试 | <具体命令，如 vitest run> |
| 单元测试（限定范围） | <如 `vitest run <路径>` / `pnpm --filter <包名> test`；不支持则写"无"> |
| 集成测试 | <具体命令或"无"> |
| Lint | <具体命令> |
| Typecheck | <具体命令> |

## UI 设计与状态清单
（若涉及 UI；每视图六维度表格 + 来源标注）

## 决策记录
> 只写当前态：选择 + 为何 + 否决了什么。**禁止时间性/演化叙事**（「原本…后来…反转…改成…」）——审计回溯交给 git。「为何否决替代」要留（它是 alternatives-considered，让人和 AI 都信服、防 fresh subagent 重新翻案，不是时间性叙事）。
### <决策点>
**决策**：<当前选择>
**理由**：<为何选它>
**否决替代**：<否决了什么 + 为何不选>

## ADR 候选
（问询中即时提议的草稿；由 Stage 6 兜底再次评估）

## 暂缓清单
（范围外但有价值的想法，记下不做、留待独立成案；无则写"无"）

## 验收标准
- [auto] AC1 — 验证命令：`...`
- [manual] AC2 — 验证步骤：<...>
```

## 完成条件

- `{{project_root}}/docs/feat-flows/<flow_id>/design.md` 存在且包含全部规定 section
- 需求源（若为外部 PRD / URL / 文档）已记入「外部参考」节
- 若涉及 UI：UI 状态清单 gap closure 完成（每项有归属来源）
- load-bearing 结论已逐个经 AskUserQuestion 由开发者拍定并记入决策记录
- TDD 基建决策已记录；若触及数据存储 / 线上行为，迁移与回滚 / 灰度已记录
- 项目命令 4 项已填（或明确标"无"），且均为非交互单次运行形式
- 术语表已收录正文出现的自造词 / 领域缩写（无则标"无"）
- 独立审计通过；与审计员的分歧（如有）已列入 Gate 审批清单

## Signal

**触发条件**：本阶段「完成条件」全部满足，**或**开发者明确表达本阶段已完成。
**动作**：用 Write 工具向 `{{flow_root}}/state/signal` 写入 `done`（引擎接受此关键词）。⚠️ **本 stage 有人工 gate，写 done 不会推进**——引擎转入 gate-pending 等开发者执行 `feat-flow approve`。收到引擎「已提交」确认后再向开发者提示 approve，别在写 signal 前就提。
