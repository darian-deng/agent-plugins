# Prototype 分流：怎么建

> 触发点：stage-1 grill（或 wayfinder working 模式 resolve 决策）中冒出"这个状态机/数据模型对不对""这个界面该长什么样"这类靠文字讨论不清楚的问题时的**非必经**分流。产出走 Bash 写 repo 外临时目录，标 throwaway，不 commit——见 stage-1.md 的元规则，本文件只补"怎么建"，不改这条。

## 先选分支，选错等于这次白做

- 问题是"这个状态机/数据模型对不对、这个 API 该长什么样、这个 edge case 处理对不对" → logic 分支
- 问题是"这个界面该长什么样、想看几个方案" → UI 分支
- 判不清时按代码类型兜底：后端模块类问题按 logic，页面/组件类问题按 UI；兜底时在产物开头写明这个假设，免得后面对着答错的问题争论。

## logic 分支

单个自包含 HTML 文件，两层严格分离：

- **纯逻辑模块**（reducer / 状态机 / 纯函数集，不碰 DOM）——这是唯一值得保留的部分，验证通过后原样提升进正式代码。
- **页面外壳**——纯粹用来操作和观察，验证完整个扔掉，不折算进正式代码。混在一起会让模块没法原样提升，只能重写一遍。

页面提供两种交互，两种都要有：

- **自由点击**：每个动作一个按钮，随时可按，顺序不限。
- **分场景走查**：每个场景一个 tab，写清"这个场景在测什么"+"该按哪些按钮"，非工程师也能照着点完——这是暴露"设计本身有问题"而不是"代码写错了"的地方。

每次操作后把完整相关状态重新渲染出来（带标签的可读面板，不是一段 JSON dump）。状态不可见等于白测——判断"这个模型对不对"全靠盯着状态变化。

## UI 分支

默认生成 3 个（封顶 5 个）**结构性**不同的变体——布局、信息层级、主操作位置不同才算变体，换个颜色/文案不算。

**默认在现有页面上加 `?variant=` 查询参数切换，不新开孤立路由**：孤立路由缺少真实的 header / 侧栏 / 数据密度，每个变体单独看都会显得"还行"，这是最容易踩的坑——原有数据获取 / 鉴权原样保留，只切换渲染的那一层。只有确实没有现成页面可挂时才退而新开一个路由，命名里带 `prototype` 字样。

切换用的浮动条要能左右切换 + 显示当前变体名，**必须在生产构建里隐藏**（判断项目的生产环境标志，如 `NODE_ENV !== 'production'` 或等价机制）——漏了这条，一旦不小心把变体代码并入正式提交，用户会在生产页面上看到这条调试用的切换栏。

## 两条分支共同的纪律

- 不装框架、不起 server、不接真实数据库——除非这次要验证的问题本身就是持久化。
- 不写测试、不做完善的错误处理——原型只回答一个问题；需要测试说明它已经不该是原型，该走正式实现。
- 验证完先把结论（选中哪个方案 / 哪个设计、为什么）捞出来写回 grilling 产出（alignment.md 或 wayfinder-map.md 对应决策条目），页面本身该扔就扔。
