# 前置产物修订协议

> 中后期 stage 发现「前面已对齐的东西要改」时统一走本协议。三个入口（开发者异议 / AI 自查 / 挑战被判不成立），前两个汇入同一套影响评估，第三个走它自己那半页。grill-flow 产物链：alignment.md（stage-1）→ spec.md + tickets.md（stage-2）→ 代码 + candidates.md（stage-3）→ review.md（stage-4）。

## 触发入口

### 入口 A — 开发者异议
开发者对当前 stage 产出有异议。**先判是否成立，不反射性接受**（"You're absolutely right"、立即改、表演性同意都是失败模式）：

| 类型 | 描述 | 处理 |
|------|------|------|
| A 事实约束 | 指出 AI 没考虑的事实约束 | 接受 |
| B 纯偏好 | 给不同写法但没理由 | 不接受，要真实考量（时间/历史/风险）；"感觉更好"不收 |
| C 冲突已有决策 | 与已记录决策冲突 | 逐项过，成立 → 影响评估 |
| D 推翻前置结论 | 推翻前置 stage 已对齐结论 | 影响评估 |

### 入口 B — AI 自查
AI 自查发现前置产物漏写/错了。直接进影响评估。**禁止自判后默默改。**

### 入口 C — 对本 flow 产物的挑战被判**不成立**

派出去的对抗审查 / 冷读子代理挑战了前置产物（`alignment.md` / `spec.md` / `tickets.md`），裁决结论是**挑战不成立、原方案保留**（判据是 `handoff.md` 第 ⑧ 格那三条：取证、平局保留在位方、裁决方自己复跑）。

⛔ **这一刻不是「翻篇」。** 成立那一侧有影响评估接着，不成立这一侧原来什么都不接——findings 记一句「不成立」就结束了。代价是同一处会被下一个 session 原样读错一遍：实测一条 flow 的指导文档被人工检查过两三遍，仍在新 session 入场时被误读成一条并不存在的前置条件，把整条流程卡住；对抗审查判定文档没错，于是文档没动，而**判「没错」恰好等于判「下一个人也会栽在这里」**。

⇒ 判不成立之后**再问一步**：**是产物不够清晰，还是这次读的人一次性看漏了？**
判据是「换一个同样认真、同样只有这些产物的读者，会不会栽在同一个地方」。

- **会** → 产物仍要改，按 L3 就地补上「那句让人不必推断的事实」（多数是把隐含前提写成显式一句，或把两处分散的判据互相指一下）。⛔ 不要顺手重构别处。
- **不会** → **什么都不动**，把这次误读连同「为什么判它是一次性失误」记在本次 flow 的 findings 段里（stage-2 是 `## 方案审查`，stage-1 是 `## 冷读缺口` 那条的下落）就够了。

⛔ **不要为了「审了一轮总得有产出」去改产物**——那和「为了交差造反驳」是同一种病（`handoff.md` 第 ⑧ 格已经钉了后者）。单向的「每轮都改一点」正是 99 分磨成 85 分的机理。

⚠️ **这一步有利益冲突**：提出主张的那一方刚输掉，由它来判「是产物不清晰」天然偏向自己。⇒ 把这个判断**一并交给审查的子代理**（派发时就写进它的任务：攻不动时要回答「换个同样认真的读者会不会栽在同一处」），或者在改动里写明「本条是主张被判不成立后提出的澄清」，让开发者认得出来。

### 成立那一侧改到什么程度为止

入口 A（C 类 / D 类）、入口 B、入口 C 的「会」，改的都是产物正文。**改到冷读者自己判断得出边界为止**，三件缺一不算改完：

1. 这条约束**防的是什么形态**（一个具体实例，不是抽象描述）；
2. **怎么验证它被满足**——能跑的命令优先于文字描述；
3. **什么情况下不适用**。

⛔ 只把结论塞进一句话不算改完：下一个人看不出边界在哪，要么改过头，要么当没看见。这一条和 `## 关键决策` 的「禁演化叙事」不冲突——写的是**当前态的边界**，不是「原本怎样、后来改成怎样」。

## 影响评估

### 1. 分级

| 等级 | 触发 | 应对 |
|------|------|------|
| **L1** | 推翻已对齐核心决策 / 范围 / User Story | **stop**，呈现问题 + 建议 abort，理由说清；确认后重 `grill-flow start`。 |
| **L2** | 漏一个约束/seam/US 子项，不推翻已有决策 | 暂停，回改对应上游产物，开发者确认后再继续 |
| **L3** | 局部命名/措辞/显然遗漏 | inline 修为当前态；按下方暴露纪律当场告知，不嵌进产物正文 |

### 2. 上游产物影响回溯（关键）

🔴 **先跑机械的那一步，再做判断的那一步：全仓 `grep -rn` 旧说法。**

1. 从开发者那句纠正里挑出**旧说法的字面词**——就是要被替换掉的那个词。⚠️ **不能取新说法**：新说法在文档里还不存在，拿它去搜命中为 0，而 0 命中读起来正好像「别处没有要改的」。
2. 对**全部已产出的产物 + 全部 flow 定义文档**各跑一次：

   ```sh
   grep -rn '<旧说法的字面词>' docs/<flow 名>s/<flow_id>/   # 全部产物
   grep -rn '<旧说法的字面词>' <flow 定义目录>/              # stages/ + references/ + scripts/
   # <flow 定义目录> 的绝对路径取 stage 提示词 [ai-flow:paths] 块的 flow_def: 行，别从上文抄
   ```

3. **把命中清单原样贴出来**（⛔ 不是「改了 N 处」这种汇总），再**逐条**处置：改成新说法，或判定不适用并写一句理由。清单上每一行都要有下落。

⛔ **这一步不许用下面的「逐一审视」代替。** 「审视」是判断动作，实测会退化成「改我眼前这一处」：某条 flow 的开发者说过一句「e2e 在本机跑，不是 CI」，AI 每次只改手上那一处，**同一件事开发者一共纠正了三次**，最后发现文档里有 **6 处**旧说法并存。**漏掉的那几处不会有任何东西报错**——没有脚本、测试或退出码在核对文档里的说法一不一致，唯一的检测器就是开发者第二次、第三次开口。grep 是机械的，所以它不会「觉得这处不用改」。

做完上面三步，再按当前 stage，逐一审视**全部**已产出的上游产物（alignment.md / wayfinder-map.md / spec.md / tickets.md / tech-design.html / 已 ship 代码 / review.md），受影响的**全部同步更新**。绝不允许"上游停留旧决策、当前产出已是新决策"的分裂状态——/clear 后任何子代理会拿到分裂的真相源。**tech-design.html 是 spec.md 与 tickets.md 两者的派生视图**（gate 主审面）：spec **或 tickets** 相关节一改，必须同步重生 HTML 对应节（`Touches` / `delivers` → 「代码库改动面」章节，`## 方案审查` → 「方案审查结论」章节），否则开发者在 gate 看到的是过期视图。⚠️ **只重切 tickets、不动 spec 的那种改法同样要重生**——`stages/stage-2.md` 第 7 步「gate-pending 期间的范围变更」就是这种形态，漏了不会有任何东西报错。

**回改一律覆盖为当前态**：产物正文改成新决策即可，**不留"原本…改成…"演化叙事**（回溯交给 git diff）。

### 3. 下游兜底
在 stage-3 触发、且 L2 改了 spec/tickets → grep 已完成 ticket（`[x]`）的改动文件，评估是否需就地在 tickets.md 追加/重切 ticket。不允许"改了 spec 但不修已 ship 代码"。

### 4. 暴露纪律 + gate 无 reject
- **L1/L2 必须停在当前位置等开发者确认**，禁止继续推进。
- **L3 禁止默默改**，在 gate 前审查清单或（无 gate 的 stage-3）当场告知。
- **gate 无 reject 语义**：开发者不批 gate ≠ 引擎回退。只能"继续讨论 → 就地改产物（spec/tickets/findings/代码）→ 重新呈现 → 再 approve"，或 abort 整个 flow。
