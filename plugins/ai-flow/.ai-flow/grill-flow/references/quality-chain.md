# 一票质量链契约（stage-3 · 第二段）

> **读者是质量链子代理**——一个**全新上下文**的子代理，接手一张已经实现完、改动留在工作树未提交的票，把它走到 commit。主 session 按本文件拼 dispatch prompt。
>
> 你的交付物 = **一笔 commit**（subject 首行含 `T<n>`、只认领本票）+ 一份精简回报。
>
> **实施段的契约在 `per-ticket-review.md`**。它的这四节对你**同样成立**，开工前照读，本文件不复述：`## 最重要的一条：路径与 cwd`、`## 有疑问先查给你的文档`、`## 安全红线五类`、`## 机器门规格`。
>
> **不属于你**：`AskUserQuestion`（人在环只在主 session 那侧）、记账（tickets.md 的 `qc:done`/`[x]`/`rm:pending`、candidates.md）、开收 worktree。**不写 `docs/grill-flows/**`**——在 worktree 里提交那里的文件会让后续所有归并被 git 阻断。
>
> ⚠️ **本文件里的 `{{flow_root}}` / `{{flow_def}}` 都是没展开的字面量**（引擎只替换 stage 提示词里的占位符；stage 提示词的 `[ai-flow:paths]` 块有 `project_root:` / `flow_root:` / `flow_def:` 三行），用之前换成主 session 给你的绝对路径——下面第 3 节另有一条同源提醒。

## 为什么这一段单独派一个新代理

实测：一个从头做到尾的实施代理，走到质量链这一步时上下文已经堆到 **40 万 token 上下**，而这一段本身要花掉整张票 **43% 的成本**（每回合均价 438K，是摸索阶段的 3.3 倍）。同样的活在一个新开的上下文里做，**起步只付 17K**（缓存读；含新建缓存的上下文总量是 45–49K），第 100 回合按契约的成本模型是 274K——实测三个 fresh 质量链代理在第 100 回合分别 277K / 264K / 262K，均值 268K，模型撑住了。**交接不是为了分工，是为了把最贵的那一段挪出最胖的那个上下文。**

由此还顺带消掉一个静默故障：实施代理交班后就不在了，「主 session 在它仍跑质量链时提交 → 三评审对着空 diff 全绿」这个形态从结构上不可能再发生。

## 开工前：先确认你接到的是什么

三种形态，主 session 会在 prompt 里写明是哪一种：

**（甲）常规**——改动留在工作树未提交：

```sh
git -C <WT> status --porcelain      # 必须非空——这就是要审的改动
git -C <WT> log --oneline -1        # 本票那笔还不该存在
```

审查对象 = `git -C <WT> diff HEAD`；末尾用 `git -C <WT> commit` 新建本票那笔。

**（乙）截断自保护**——prompt 里写明「本票已有 `[partial]` commit」：上一轮实施代理撞到上限，把做完的部分提交成了一笔标 `[partial]` 的 commit。**剩余的实施工作不归你**：主 session 会先另派实施代理按剩余清单续做，那一轮照常不 commit，所以你接到手时**那笔 `[partial]` 和未提交的续做改动同时存在**。

```sh
git -C <WT> log --oneline -1        # 必须看到本票那笔，subject 带 [partial]
git -C <WT> status --porcelain      # 续做的改动
```

审查对象 = **`git -C <WT> diff HEAD~1`**——一条命令就覆盖「那笔 `[partial]` + 续做的未提交改动」的全部，干净树脏树同一写法。⛔ 别用 `show HEAD` 并上 `diff HEAD`：续做轮改写过的行会出现两次（先作为 `[partial]` 的新增、再作为对它的修改），评审读到同一处代码的两个版本并列，最容易把 correctness 判反。末尾用 `git -C <WT> commit --amend` **折回那笔**并去掉 `[partial]` 标记，保住一票一 commit。

⛔ **fail-closed：prompt 里的剩余清单非空、而 `status --porcelain` 是空的 → 不许 amend。** 停下报「受阻」，正文写「剩余清单未标完成而工作树无改动，续做段可能没派或没交付」。这一格是本形态唯一会**静默**交付半成品的地方：只审那笔 `[partial]`、三评审全绿、`--amend` 摘掉标记之后，票面上再没有任何东西说它没做完，而机器门的四条断言（subject 含票号 / 历史线性 / 实改文件 ⊆ `Touches` / diff 非空）**全部会过**。清单标了「已由续做代理做完」或「无剩余」，树才允许是干净的——那种情况只审那一笔。

⛔ **无论树干净与否，都不要自己去做剩余实施。** 这条曾经反过来写（「剩余工作清单也在 prompt 里，先把它做完再进三评审」），实测一次运行里质量链代理照办，跑成 483 轮 / 上下文 784K。要命的不是补做本身花的那 44.7%，是它把补做之后的 183 轮评审全部推到 520–784K 的上下文上跑：那 183 轮花了 117M，而同一次运行里一个真正从 17K 起步的质量链代理，前 183 轮只累计 46M。**先实施后评审挤进同一个上下文，光这个顺序就多花约 71M**，相当于把「另开上下文」买来的东西原样退回去。

**（丙）复派**——prompt 里写明「本票那笔 commit 已存在，本轮任务是 <修 findings / rebase 适配>」：上一轮质量链已经交付过，所以工作树是干净的、本票那笔正常 commit 已在（不带 `[partial]`）。

```sh
git -C <WT> log --oneline -1        # 必须看到本票那笔，subject 不带 [partial]
```

审查对象 = **`git -C <WT> diff HEAD~1`**（与形态乙同一写法、同一理由——见上，⛔ 别用 `show HEAD` 并上 `diff HEAD`，那会让你改过的行出现两次）；末尾 `git -C <WT> commit --amend` **折回那笔**。⛔ **绝不另起一笔** `fix(T<n>)`——机器门③ 的票↔commit 配对只会认领其中一笔，另一笔的实际改动整个逃过断言⑥ 的 `Touches` 核对而全绿。

⛔ **三种形态都对不上（树干净、既没有 `[partial]` 也没有本票 commit）** → 停下报「受阻」，正文写「接到的工作树无未提交改动、也无本票 commit，实施段可能没交付或改动已被别人提交」。**不要自己去实现这张票**——那是实施段的事，你没有它的上下文，重做只会产出第二套实现。

## 派发时带什么（主 session 机械拼装）

`<FD>` = 本文件所在目录的上一级（定义层：`references/` `scripts/` 在这儿）；`<FR>` = 项目里的 `.ai-flow/<flow>`（`state/` 在这儿）。就是 stage-3 提示词 `[ai-flow:paths]` 块里 `flow_def:` / `flow_root:` 那两行展开出来的绝对路径。子代理没有占位符注入，**下面凡是路径都要给绝对路径**。

- `<WT>` 与（monorepo 时）`<WT_ROOT>` 绝对路径 + cwd 纪律
- **该票票面整段**（票行 + `delivers` + `Blocked by` + `Touches` + `AC`）——`Touches` 是第 6 步自检的对照物，缺了那一项做不了
- **spec 相关段**（Spec 轴要用）——切好给，⛔ 不给 `spec.md` 路径
- **前置/后继票关系**（票号 + 一句结论 + 它那笔 commit 的 sha）——第 5 步撞 pre-commit hook 时 `--no-verify` 的唯一依据
- **实施代理回报里的「取舍与为什么不选 X」整段**——你没写过这段代码，缺了它评审一问原因就只能上报
- `<FD>/references/fowler-smells.md` 的**绝对路径**（Standards 轴要携全文）
- 形态是甲 / 乙 / 丙（见上）；**乙的话附上票面 `rest:` 字段的内容 + 它的完成状态**（「已由续做代理做完」/「无剩余」——⛔ 只丢一份清单过去，收到的人无法判断该不该等，见形态乙那条 fail-closed）；丙的话写明本轮任务是修 findings 还是 rebase 适配
- ⛔ **不给 `tickets.md` / `spec.md` / `gate-stage-3.cjs` 的路径**（都是大文件，给了路径就被整篇读进来，此后每一轮都重新计费；实测被整篇读过 14 / — / 15 次）

## 固定顺序

### 0. `/simplify`(apply) —— Claude Code **内置**斜杠命令

机械质量修（复用 / 简化 / 效率）。**必须跑在三评审之前**——三个轴的职责定义就是「只报 simplify 修不动的判断型问题」，顺序反了它们会把本该机械修掉的一整类问题当判断型上报，或者干脆按定义放过。改动仍不 commit。

**怎么调**：`Skill` 工具，`skill: "simplify"`，`args` = 本票改动文件的绝对路径清单（空格分隔）。

⛔ **搜不到不等于没装。** 它编译在 CLI 二进制里，磁盘上没有对应文件——`~/.claude/commands/`、各插件的 `commands/`、项目 `.claude/` 全都翻不到。**别据此判「本机没装」而跳过这一步、或改成自己手做**（实测发生过一次：搜了四个位置、写下「本机没装 `/simplify`」、以自审顶替）。也别拿名字相近的东西顶替——`code-simplifier` 这个名字在各仓库同时以插件、项目级 skill、code-review 评审轴三种身份出现过，都不是它。

⛔ **必须传文件清单。** 不传 `args`，它按自己的 Phase 0 去跑 `git diff @{upstream}...HEAD`——那条命令在**你的 cwd** 求值、不认 `<WT>`，拿到的是空 diff 或别票的改动，而它照样返回「无 finding」且不报任何错（与 `per-ticket-review.md` 开头那条静默空转同源）。清单取自 `git -C <WT> diff HEAD --name-only`（形态乙 / 丙用 `diff HEAD~1 --name-only`），逐条拼成以 `<WT>/` 开头的绝对路径。

**它的提示词会让你「用 Agent 工具并发派 4 个清理轴」——⛔ 不要照做。** 你是子代理，从你这一层派出去的孙代理**一定异步、且你没有被它唤醒的能力**（原因见文末「为什么不许再往下派」）。⇒ **自己顺序走完那四个轴**（复用 / 简化 / 效率 / altitude），一轮一个轴、不要混着看。

### 1. 三评审（**自己顺序审，⛔ 不许派孙代理**）

三个轴都 report-only、不写文件、只读同一份未提交 `git diff`。

⛔ **不许用 Agent 工具往下派。** 你没有「挂起」态，也**没有被孙代理唤醒的能力**：派完你就无事可做，只能结束回合（宿主会把它记成「这一票交付了」，而你一行都没提交），或者靠一轮轮 `Bash: true` 空烧来等——每个空转回合都要为当时的全部上下文付一次全额。实测一次运行里 **157/311 次子代理派发跑在后台**，随后产生 **422 个纯空转回合**，最多的一张票烧掉 178 轮。

⚠️ **这不是纪律问题，是能力问题。** `run_in_background` 在「子代理派孙代理」这一层**根本不生效**：实测有过一次对照——某质量链代理显式传了 `{"run_in_background":"false"}`，工具结果仍然是「Async agent launched successfully… working in the background」；这个参数也从未出现在 Agent 工具的 schema 里。本文件此前要求「必须同步派发」，要求的是一个不存在的开关，**实测被违反 9 次**（每次约 90K token + 5–6 分钟空转，靠主 session 手动 `SendMessage` 救回）。

⇒ **自己按三个轴各审一遍，一轮一个轴、不要混着看，每轮只戴一个轴的眼镜。** 回报里写明「三评审为自审」。

⛔ **每个评审的第一步必须是断言那份 diff 非空**（`git -C <WT> diff HEAD --stat`，零行就停下、状态报「受阻」，正文写「diff 为空，改动可能已被提交」）。**形态乙 / 丙下这条对 `git -C <WT> diff HEAD~1 --stat` 求值**——那两种形态本票的改动已经在 HEAD 里，对 `diff HEAD` 求值会让三个评审各自报「受阻：diff 为空」，质量链空转一轮。理由：如果有人在评审读的时候把改动提交了，`git diff HEAD` 就变空，三个评审会各自对着空 diff 写出一份「没发现问题」——**而这不会报任何错误**，「真的没发现」和「读到空 diff」在回报里长得一模一样。实测发生过一次，事后只有一个轴能确认它读到了真实改动。这条断言是这个静默模式唯一的机器可查点。

三个轴：

- **Standards 轴**：携 `<FD>/references/fowler-smells.md` 全文（主 session 会给绝对路径），只报 simplify 修不动的判断型 smell（架构级重复、错 altitude、过度工程）。这是 mattpocock 的质量轴，别退化成 correctness。
- **Spec 轴**：携 spec 相关段（主 session 会切好给你，**不要自己去整篇读 spec.md**），查该票对 spec 的一致性（偏离 / 漏实现 User Story / 越出 spec）。
- **correctness 轴**：专审 bug——逻辑错误、边界/空值、错误处理与失败路径、并发/竞态、**测试完整性**（diff 里凡涉及测试文件，逐条核对断言数量/强度相对改动前是否被弱化——弱化了但实施代理的回报没有在「取舍与为什么不选 X」段说明理由 → 报 finding，判断型，交主 session 裁），以及**安全红线五类**（定义见 `per-ticket-review.md`）。不依赖任何内置 slash 命令，任何仓库通用。

⛔ **一轴都不许省。** 自审最容易坏在这里——三个轴混成一遍「整体看看」，回报里看不出缺了哪块，而这一票的质量链就静默缺了一角。三轴的职责定义互不重叠（上面三条），逐轴走。

⛔ **三个轴全部审完之前，你还没走到第 2 步。** 中途停下会被宿主记成「这一票交付了」（它在你「没有存活的后台子进程」时就给主 session 发完成通知），而你其实一行都没提交。要么审完，要么按第 6 步报「受阻」。

> **待验证的下一步（本轮先不做）**：三评审改由**主 session** 派三个独立 `opus`（depth-1 派发能被正确唤醒，主循环里批内实施代理并行派发就是这个模式）。那样能拿回「三个独立视角」的质量，代价是主 session 每票多吸收约 1 万字符（实测三评审回报均值 3340 字符 × 3），且要在一票中间串行等两轮、同时还在并行调度 3 张票。等本轮自审形态跑出数据再定。

### 2. 裁 findings

按可裁性分两类，别混：

- **机械型**（明确的 bug、spec-drift、simplify 修不动但改法唯一的 smell）→ 就地修（仍不 commit）。
- **判断型 / 决策型 / 安全型**（要不要重构、是否过度工程、方案层争议、推翻既定方案、命中安全红线五类）→ **不自行处置、不 commit、不塞进 candidates 蒙混**，连同评审原文与你的看法一起**回报**，由主 session（`opus`）裁。安全红线是全流程唯一的人在环落点，只在主 session 那侧。

⚠️ **你没写过这段代码**，所以「作者当时为什么这么选」这类问题查不到依据时**一律归为判断型上报**，不要替实施段辩护、也不要替它改。

### 3. 注释清理 —— ⛔ **不再属于你，跳过这一步**

**已上收给主 session**，落在「该票 commit 之后、`close` 之前」。你不碰它，回报里也不用提它。

三条理由，都来自实测：
- `comment` 的核心判据是**陌生读者冷读**（「只看代码 + 跳定义处能否得出同样信息」）。你已经读过这一票的全部改动，不是陌生读者——自审会让这条判据静默失效，而回报里看不出来。它需要 fresh context，而 fresh context 只有主 session 派得出来（depth-1 能被唤醒）。
- 它是**写操作**，且耗时是分钟量级。**当前形态实测：114–557 秒，均值 418**（同一个 flow 实例的 12 个清理代理，各自 transcript 首末时间戳之差）。⚠️ **本条曾记「898.8 秒 / 837.9 秒」，那两个数字在当前形态下不成立**——最慢那次只有 898.8 的 62%；它们来自**注释清理还在质量链代理内部、由它同步等**的旧形态（连同旧形态下「是三评审回报耗时的 3.5–9.3 倍」那个比较一起作废——当前形态下没有同口径的三评审样本，所以下面不再拿它和三评审比）（旧成本模型整体作废见 `execution-unit.md` 的「实际峰值并发」节，但那两个秒数一直没跟着更新）。⚠️ 这个区间也**不是主 session 的等待时长**：上收之后派发是异步丢后台的，实测 12 次派发的 `tool_use → tool_result` 间隔只有 2–12 秒。**换掉的只是数字，下面两次事故仍然是有效的设计约束**——放在 commit 之前，等待窗口必然被撑破：一次是等不到就先 commit、清理代理随后陆续落改动，**一张票裂成 4 笔 commit**（破了「一票一 commit」，主 session 事后 `git reset --soft` 收拾）；另一次是等不到就**自己动手改同一批文件**、和仍在跑的清理代理撞车，误删三处注释指针（`DEFECT-WSNOTIFY-01` 的归属指针等）。
- 移出 commit 窗口之后，它迟到也不再影响 commit 边界。

**主 session 侧怎么做**（stage-3 主循环第 5 步指到这里）：派一个 fresh-context 子代理调
`comment`（`Skill` 工具，`skill: "ai-flow:comment"`，范围 = 本票那笔 commit 的改动；
⛔ 别去 `Read` 插件目录的 `SKILL.md`——那里并存十几个历史版本，实测挑中过五天前的旧版），
它改完由主 session `git -C <WT> commit --amend` 折回本票那笔。
⚠️ 它耗时 2–9 分钟（上面那个 114–557 秒区间）⇒ **丢后台去推别的票**，别原地等（主 session 会被完成通知唤醒，
这是它有而子代理没有的能力）。

🔴 **派发 prompt 里必须写死这两条，否则「上收」只解决了「谁来派」、没解决「它自己会不会再往下派」：**

1. ⛔ **它自己不许再用 `Agent` 工具往下派，`comment` 的每一步都自己顺序走完。**
   `comment` 那份 SKILL.md 的「执行模型」节要求调用方「派 fresh-context 子代理群、
   一子代理认领一批、并发 ≤5」——承接代理照着做就又是子代理派孙代理，落回本文件文末那个陷阱
   （这个形态在本 flow 已付过两次代价：一张票裂成 4 笔 commit、一次把 12.6 分钟的正常耗时误判成超时）。
   ⇒ prompt 里点明它**同时扮演** skill 里的两个角色：调用方那半的「选文件 + 切批」，
   和子代理那半的逐文件判删。**并发从 ≤5 降到 1 就是这个方案付的代价**——可接受，因为范围只是
   本票那笔 commit，通常几个文件，而实测单票 114–557 秒本来就是顺序量级。
2. ⛔ **不要执行 typecheck / lint / 测试命令。**（⚠️ 措辞必须点出「执行」和「命令」：
   读测试源码是 `comment` 核心判据「盖住测试」的必需输入，写成「不要跑任何测试」会被读成
   「不要参考测试」，判据当场垮掉。skill 原本要求调用方把这条带进 dispatch prompt，
   现在调用方是你。）

🔴 **`comment` 最后那步「汇总核实」归你（主 session），不归它。它是 `--amend` 之前必须跑命令的一道门，不是「顺手看一眼 diff」。** 那一步的机制是「以 `git diff` 为唯一事实源、不采信执行方自报」，靠的是核实方与执行方是两个人；它自己顺序做，这层对立就没了（实测过执行方编造报告：声称改了没碰的文件、虚构原文）。

⚠️ **写成散文就等于没有——这条实测漏过。** 本段曾只写「你 `--amend` 之前反正要看 diff，顺手核三条：①…②测试文件零改动；③…」，结果一张票的清理代理**改了测试文件**（`…/services/recording/__tests__/recordingService.test.ts`，12 行）而 `--amend` 照样把它折了进去。`comment` 那份 skill 明文「测试文件（`*.test.*` / `*.spec.*` / `__tests__/` / `tests/`）不扫、不删、不做 Step 3」，理由之一正是测试的回归锚注释形似「复述测试名」最易被误杀却恰恰删不得——而那次被删的里面确实有一条真跨文件指针（指向另一个测试文件的文件头散文，go-to-definition 到不了，按 skill 属于「唯一可留的指针」）。⇒ **要跑命令、要看输出、要在被唤醒的那一轮当场做**：清理是丢后台的，通知到达时你已经在推别的票，这三条早就掉出注意范围了。

⚠️ **只在完成通知到达之后跑这道门**（那时清理代理已经停了）。⛔ **它还在飞的时候别提前核、更别自己动手改那批文件**——那正是上面第二次事故的形态（主 session 与仍在跑的清理代理撞车、误删三处注释指针）。

**派发前先记下 `<PRE>` = 本票那笔 commit 的 sha**（`git -C <WT> rev-parse HEAD`）——它是清理代理开工前的树，下面三条和撤销全以它为基准。

```sh
# ② 测试文件零改动 —— 放第一条跑，非空即违规（这一条实测漏过）
git -C <WT> diff --name-only <PRE> | grep -E '\.(test|spec)\.|(^|/)__tests__/|(^|/)tests?/' || echo 'OK: 测试文件零改动'
# ① 实际改动文件 ⊆ 本票 Touches
git -C <WT> diff --name-only <PRE>
# ③ 非注释行改动为 0 —— 看这份 diff，只该有注释行的增删
git -C <WT> diff <PRE>
```

**违规按条分开处置（撤销粒度 = 违规粒度，别一刀切）：**

- **② 命中 → 只撤测试文件那部分、保留其余，再 amend**：`git -C <WT> checkout <PRE> -- <命中的那些测试文件>`，然后**重跑 ② 直到打印 `OK`**。⛔ **不要整体拒绝 amend 报受阻**：生产文件上的清理已经做完了，整份丢掉要么重付那 2–9 分钟重跑一遍、要么把这张票的清理整段跳过——而 `cm:done` 照样会被写上，`/clear` 之后没有任何东西看得出它没做；何况 `close` 之前是 `--amend` 唯一可用的窗口，报受阻等于把窗口耗掉。
- **③ 命中，且改动对不上它回报里逐条记的「搬迁」→ 撤回那些文件**（`git -C <WT> checkout <PRE> -- <那些文件>`），别 amend 它们。**动作与诊断解耦**——越权和漏记都不采信，两种都撤。
- **① 命中（改到本票 `Touches` 之外）→ 同样 `checkout <PRE> --` 撤回那些文件**：`Touches` 之外的改动会让机器门在 stage-4 报越界。
- 三条都撤干净、② 打印 `OK` 之后才 `git -C <WT> commit --amend`。**撤销全发生在 amend 之前、且只碰本票 worktree 里的文件**——所以不会多出第二笔 commit（「一票一 commit」不破），也不会碰任何仍在跑的别票。
- 撤了东西就在回报/记账里写一句撤了什么，别静默——下一次同类违规该改的是派发文案，不是每票手撤。

🔴 **改完立刻在票面写 `cm:done`**（与 `qc:done` 同一口径：该票行内或其缩进子项）。它是这一步
唯一的落盘痕迹——没有它，`/clear` 之后重入会把这张票读成「已交付未回合」而直接去 close，
**注释清理被静默跳过、且票面上没有任何东西看得出它没做**（`reentry.md` 相位表专门加了一行拦这个）。

⚠️ **务必在 `close` 之前做完**——`close` 一旦 ff 进需求分支，`--amend` 就不可用了，
那时补的清理只能另起一笔，等于把「一票一 commit」的问题从票内搬到批次层。

### 4. 客观地板（范围 = 前台预算内跑得完的那些）

typecheck + **本票测试** + **本票直接影响到的包 / 目录的测试** + **假绿检测**（测试选择器实际匹配 ≥1 个测试——runner 过滤器打空会 exit 0，这是工具属性）+ **枚举负空间**（本票蕴含 N 个错误码/状态/分支时，逐项核 diff 都实现且有断言）。

⛔ **不要跑整仓全量测试，也不要把任何命令丢后台。** 这不是为了省时间，是因为**你没有「挂起」这个状态**：

- 一条前台命令有超时上限，整仓全量（本仓网页端 ≈2 万条用例）跑不完；
- 于是唯一的出路是 `run_in_background`，而丢后台之后你无事可做、只能结束本轮；
- **结束本轮 = 你被终止**。宿主随即给主 session 发一条 `completed`，正文是你最后那句「在等 X」——它读起来像「还在跑」，于是主 session 就一直等下去。实测这个形态发生过 **8 次以上**，最长一次空转 **1 小时 07 分**，而那期间后台进程早就被 OOM 杀掉了。
- 主 session 那一侧没有这个问题（它被后台命令的完成唤醒过，实测有效）。所以**整仓全量回归属于主 session 的批次收口**，不属于你——它跑在**归并之后**的树上，那才是回归真正该测的对象，而且不会跑 N 遍。

**本票直接影响到的包 / 目录**怎么定：`Touches` 覆盖到哪些包 / 顶层目录，就跑哪些的测试（`vitest run <目录>` / `--filter <包>`）。跑不完就再切细，⛔ 不许因此改用后台。**给每条长跑命令设超时**（优先用宿主 Bash 工具自带的 timeout 参数；shell 的 `timeout 900 …` 要先确认它存在，macOS 默认没有）——无限期挂住会被看门狗判成 stalled，那时连回报都没有（实测发生过）。

⛔ **门禁命令只回摘要，不要把整段日志灌进上下文。** 用 `2>&1 | tail -40`、或只回「失败条目 + 计数」。跑绿的那次尤其只需要一行结论——实测单个代理内跑过 41 次 typecheck、33 次 lint，每一次的整段输出此后每一轮都在重新计费，而除了最后一次全部已经作废。

**回归纪律仍然成立**：你跑到的范围内，既有测试挂了默认当回归。范围外的回归由收口那一次全量兜。

- **几条车道同时跑全量测试会互相抢 CPU**，超时型断言零星变红。判据：失败散在少数几个文件、单独重跑或调大 `--testTimeout` 就过、`uptime` 的 load average 明显偏高（实测撞到过 load 71）——资源争抢不是回归。与下面那条的区别：这条是**用例数不变、少数用例超时**，下面那条是**大批文件加载失败、总用例数变少**。
- **失败文件数 ≫ 失败用例数、且总用例数明显变少 = 依赖陈旧，不是回归。** 先把依赖装上再重跑，别开始读代码：那是 `node_modules` 相对锁文件过期导致大批文件收集不起来，runner 把「文件加载失败」计成「文件失败」。真回归的形状是「文件数不变、少量用例红」。
- **本票新增了任何会挡住别人的检查**（CI job、lint 规则、pre-commit 钩子、校验脚本）→ 地板多一条：**对全部存量跑一遍**，把原始输出贴进 commit message 与回报。绿 → 说明。红 → 逐条说清哪些红是设计如此（指出票面依据或后续哪张票消掉）、哪些红**没有归属**。没有归属的红必须上报，⛔ **不许自行加白名单或基线机制**——那是把债重新藏起来，属于第 2 步的判断型 finding，由主 session 裁。同时核一遍这道闸**在 CI 与在开发机上判定一致**（典型偏差源：被 gitignore 忽略的目录、符号链接、只有开发机才有的工作树——实测出过一次「开发机恒红、CI 恒绿」，那是最坏的一种门禁，会训练人忽略它）。

### 5. commit（只含代码）

一次性提交为本票唯一那笔，**subject 首行必须含 `T<n>` 且只含本票号**。机器门只解析 subject、不看 body。

**在 `git add -A` 之后、`git commit` 之前**，取一次本票的规模数字，等下要写进回报（第 6 步的 `qc-metrics` 行）：

```sh
git -C <WT> diff --shortstat --cached HEAD      # 形态乙 / 丙用 HEAD~1
```

⛔ **时点和 `--cached` 都不能省**。`git diff --shortstat HEAD`（不加 `--cached`）**不含未追踪的新文件**——一张纯新增文件的票会记成 0；而同一条命令在 `git add` 之前和之后答案不同（实测：1 个已追踪文件改 2 行 + 1 个 40 行新文件，add 前是 2 行、add 后是 42 行，**21 倍**）。先 add 再加 `--cached` 让三种形态量的都是同一个东西：本票相对起点的全部改动、含新文件。

**撞 pre-commit hook 时**：本 flow 的切片策略**刻意**会产出中间不可编译态（wide-refactor 走 expand → 分批迁移 → contract）。能在主 session 给你的「前置/后继票关系」里指出**具体依据**（哪张票会补齐）→ `git commit --no-verify`，跳过原因写 body 不写 subject（双 `-m`，subject 首行仍只含本票号）；指不出依据 → 当实施缺陷正常修掉再提交，不许套用本条。

### 6. 回报（精简形状）

状态（**完成 / 完成但有顾虑 / 受阻 / 需补充信息——只有这四种；本票那笔 commit 还没落下就一定不是「完成」**）+ 改了哪些文件做了什么 + 沉淀候选 + 需主 session 落账或拍板的项：

- **首行必须是** `commit: <sha>` 或 `未提交，原因：<一句>`。主 session 靠它判相位，缺了就只能再派一轮。
- **第二行必须是本票的规模记账**（格式固定，⛔ 不要改字段名或加空格；主 session 会原样抄进 tickets.md）：
  ```
  qc-metrics: diff=<第 5 步量到的 insertions + deletions> simplify=<simplify 返回的 finding 条数> axes=<三轴 findings 条数>
  ```
  两个条数按你实际收到的填，一条都没有就写 `0`。`simplify=` 数的是 `/simplify` 本轮返回的 finding **总条数**（不分轴——那一步的轴名不在你的契约里，别猜）。
  **为什么要它**：这一段的成本有一个规模无关的地板（实测回归截距 3.22M，最小的一张票——13 行 diff——实测 3.71M，是它实施段 0.846M 的 4.38 倍（含子孙代理的子树口径）），而**票的大小事前预测不了**（`stage-2.md` 记着实测：票面声明的改动路径数与实际工作量的秩相关 0.15、字数 0.12、六特征回归交叉验证 R² 为负）。所以「小票该不该减配」只能靠事后样本判，而现在样本量是 1。⛔ **别把这一行写进 commit body**——stage-4 的 squash 会 `git reset` 摊平、用全新 message 重提，再 `git branch -D` 删掉票分支，那些 per-ticket commit 连引用都不剩（实测 squash 后 `git log --format=%b | grep -c qc-metrics` = 0）。写进 tickets.md 才随 squash 永久留在仓库里，日后 `grep -rn qc-metrics docs/grill-flows/` 一条命令跨 flow 汇总。
- ⛔ **「我在等 X」不是一种状态。** 评审子代理没齐、测试还在跑——那些时候你没有可交付的东西，返回等于向主 session 谎报完成（宿主会照发 `completed`）。两条出路：① 同步等到底；② 确实等不到（工具挂死、超时）→ 状态写**受阻**，正文第一句写清「卡在哪一步 / 工作树里现在有什么 / 从哪继续」。
- **回报之前先确认这棵树上没有别人在写**：按本文件的契约你**不该派出过任何子代理**（三评审自审、simplify 自己走四轴、注释清理已上收），所以树上只该有你自己的改动。回报前重跑一次 `git -C <WT> status --porcelain` 并把结果写进回报——如果它和你以为的不一样，说明有东西比你活得久还在写这棵树，⛔ 别 commit，报「受阻」。
- **`Touches` 自检结论（必填，没越界也要写）**：把 `git -C <WT> show --name-only --format= HEAD` 逐条对照本票声明的 `Touches`，写成「全部落在声明内」或「以下 N 条越出声明：<路径> —— 各自的理由」。理由要能让主 session 二选一：**这改动确实属于本票**（→ 它补声明）还是**这其实是另一件事**（→ 它拆票）。⛔ 你自己不要改 tickets.md。漏报的代价：最早的发现点变成 stage-3 结尾那道机器门，而那时 worktree 已拆、commit 已归并，两种处置已经分不开了。
- **本轮做过 `git commit --amend` 的**：给出可一行核验的三元组——`被 amend 的 sha（我在本轮第几步创建的）/ 它的父提交 sha / 本次新增暂存的文件数`。宿主会对 `--amend` 报 `[Git Destructive]` 安全告警，**那是准确判定不是误报**。实测这条告警在一次运行里出现 4 次。
- 第 2 步的判断型 / 决策型 / 安全型 findings（附评审原文）
- **需真机验证**——判据是「机器地板验不了的」：触发原生 / 主进程运行时、鉴权登录态流转、设备 I/O、跨端真机行为等。**漏报的代价是静默的**：主 session 据此打 `rm:pending`，而 stage-4 的收口**只认该段登记过的票**（没登记 = 对收口方不存在），于是全流程唯一的真机验证落点被整段跳过，且不报错。宁可多报一条让开发者驳掉。

## 归并前自适配（并行票）

**这件事归你，不归实施代理**（你手上已经有地板和 `--amend` 两步）。

**触发时机**：主 session 回合本票失败、把票退回来——那说明别的票已经先回合了。

```sh
node <FD>/scripts/worktree.cjs --flow-dir <FR> sync <flow_id> <T<n>|R<n>>   # rebase 到需求分支；车道模式用本车道的 R 号
# 有冲突 → 在 <WT> 里解 → git -C <WT> rebase --continue
```

⛔ **用 `sync` 而不是自己敲 `git rebase <某分支>`**：需求分支叫什么只有主仓知道（`git branch --show-current`），照字面跑 `git rebase main` 会把本票 replay 到 main 之上，此后回合永久失败而你看不出错在哪。

⛔ **绝不用 `git merge`（含 `-X ours`）做适配**，两个理由都实测过：`-X ours` 在无文本冲突时输出 `Auto-merging` 并**静默丢弃**一侧改动，而 `--ff-only` 会把这个结果照单收进主历史（`close` 现在会拦，机器门④ 是最后兜底）；且 merge 之后 `git commit --amend` 改的是 merge commit 而不是本票那笔，冲突路径下更是直接 `fatal: You are in the middle of a merge -- cannot amend`。

适配完**重跑上面第 4 步的地板**，再 `git -C <WT> commit --amend` 折回本票那笔。

**适配有时不得不改另一票的文件**（往对方新建的 registry 里注册这类）。照做，然后在回报里点明——机器门⑥⑦ 会因此报越界/相交，那是预期情形，由主 session 按门的提示补 `Touches`，或把该票移出本批（补 `Blocked by` + 单独成批）。⛔ **不是撤掉 `batch:` 标记**——那是机器门⑦ 唯一的触发条件，删了等于把并行安全的机器依据整个关掉。

## 为什么不许再往下派

**「子代理往下派孙代理」这一层是结构性异步的，而且没有开关能关掉它。**

有对照实验：某质量链代理连着派了 8 次（三评审 3 个、simplify 四轴 4 个、注释清理 1 个），
每次拿回的都是同一句「Async agent launched successfully… working in the background」；
第 9 次它显式传了 `{"run_in_background": "false"}` 去试——**结果一模一样**。
这个参数从未出现在 Agent 工具的 schema 里，在这个深度它不是一个真实开关。

**而唤醒能力只有顶层有。** 主 session 能被后台派发的完成通知唤醒（主循环里批内实施代理
并行派发就依赖这个），子代理没有这个能力。所以子代理派出孙代理之后只有两条路：
结束回合（宿主把它记成「这一票交付了」，而它一行都没提交），或者用 `Bash: true` 空烧着等。

**代价是实测出来的**：这一形态在一次 flow 里发生 **9 次**（票号 T19 · T23 · T11 · T35 ·
T50 两次 · T36 及更早若干），每次约 **90K token + 5–6 分钟**，全靠主 session 手动
`SendMessage` 把它救回来续跑。而本文件此前的应对是往「必须同步派发」上加更强的措辞——
那条规则要求的是一个不存在的旋钮，加措辞不会让它出现。

⇒ **契约改成：这一段里凡是需要「派出去等结果」的，要么你自己顺序做完，要么上收给主 session。**
你自己不派任何 Agent。
