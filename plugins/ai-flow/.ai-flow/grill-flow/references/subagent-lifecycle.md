# 子代理生命周期：谁可以等、通知怎么读、失联怎么救

> **触发**（撞上任意一条就读本文件）：要派一个子代理；收到宿主的「完成」通知、准备去动那棵工作树；`worktree.cjs status` 显示某车道静默 ≥30 分钟；某个子代理迟迟没回报。
> `<WT>` = 该票 worktree 里的项目根（`worktree.cjs open` 打印的那个）。

## 一、谁可以等：这条决定了派不派子代理

**只有能被唤醒的执行体才可以等待。** 实测的不对称，两侧都反复验证过：

- **主 session 可以等**：它丢后台的命令完成后会把它唤醒（实测有效多次）。
- **子代理不能等**：它一旦结束回合就是**终止**——这个宿主里子代理没有「挂起」态。它丢后台之后无事可做、只能结束回合，于是自杀；宿主随即给你发一条 `completed`，正文是它最后那句「在等 X」。这个形态在一次运行里出现 **8 次以上**，最长一次空转 **1 小时 07 分**。

由此得出的两条硬规则，stage-3 主循环里各留了一行，理由在这里：

- ⛔ **不要为「只跑验证」派子代理**（rebase 后重跑地板、收口测试、复跑某条命令取数字这类）。派子代理的收益是省 context，而这类任务的输出只有几行数字、几乎不费 context，却把工作放到了唯一不能等待的一侧——**净亏**。实测两次停滞正是这类：两个「rebase 后重跑地板」的子代理各自 6–9 次工具调用、不到一分钟就停住，什么都没产出。**这类活主 session 自己跑，丢后台，它会被唤醒。**
- ⛔ **派发提示词里不要给子代理下「整仓全量」的地板要求**（更不要给 `≥ 1623 文件 / 20126 通过` 这种全量数字目标）。整仓全量超出前台单条命令的超时上限，等于逼它丢后台、也就是逼它自杀。子代理的地板范围是「typecheck + 本票测试 + 本票直接影响到的包/目录」，**整仓全量回归是主 session 在收口时跑的**——那一次跑在归并后的树上，才是回归真正该测的对象，而且一轮只跑一次而不是每票各跑一遍。

## 二、收到「完成」通知之后、动那棵工作树之前

**完成通知不等于那个子代理已经停了。** 宿主在 agent「这一轮结束且没有存活的后台子进程」时就发通知，而它可以再被唤醒继续跑；它派出去的孙代理（三评审、`comment` skill 的 fan-out）也可能还活着并继续写那棵树。

**先做一次机械判定，再读正文**——一票走两段，判据按你派的是哪一段分两套：**实施代理**的首行必须是 `impl-done: <N> 个文件已改，未提交`（配 `git -C <WT> status --porcelain` 非空复核）；**质量链代理**的首行必须是 `commit: <sha>`。首行不是对应的那个 → **这一票没交付**，不管 `<status>` 写的是不是 `completed`（宿主对「干完了」和「停下了」发的是同一种通知，正文才是差别，而正文很容易被读成相反的意思——实测「Waiting for the full web4 test suite」被读成了「它还在跑」，然后等了 1 小时 07 分）。首行判据是唯一不需要理解正文的判据，**先跑它**。

**然后核对应的那两条，都对上才动那棵树**（提交 / rebase / 另派子代理进去）：

```sh
# 实施代理交付后（它不 commit，所以树必须是脏的）
git -C <WT> status --porcelain      # 必须**非空**
git -C <WT> log --oneline -1        # 不该有本票的新 commit（截断自保护的 [partial] 除外）

# 质量链代理交付后
git -C <WT> status --porcelain      # 必须为空
git -C <WT> rev-parse HEAD          # 必须等于它回报里的那个 sha
```

⚠️ **别把两套用混**：实施代理交付后树本来就是脏的，拿「必须为空」去核它会永远判成「它还没停」，于是质量链永远派不出去——而这正是本文件要根治的那种空转。

对不上就是它还没停——等，或者用 SendMessage 问它，**不要动**。

⛔ **为什么这条是硬的**：一票的质量链里，三个评审读的是**未提交**的改动（`git diff HEAD`）。你在它们读的时候提交，diff 就变空——**三个评审会各自对着空 diff 写出一份「没发现问题」，而这不会报任何错误**。「真的没发现」和「读到空 diff」长得一模一样。实测发生过一次：主 session 在实施子代理仍在跑质量链时提交、并另派子代理进同一棵树，两边来回踩了三轮（一边提交、一边 `git reset` 撤回继续跑），事后只有 Standards 轴能确认读到了真实改动，另外两轴只能对**已提交的完整 diff** 重跑补验。

**已经踩了怎么办**：别假装没发生。对已提交的那笔完整 diff 重新派对应轴的评审补验（那时不存在空 diff 风险），结论如实告诉开发者；补验若挖出真问题而票已回合，就是安全红线里「已合入才发现」的情形——停下问开发者。

## 三、失联 / 停在等待怎么救

宿主的完成通知**不区分「干完了」和「停下了」**：子代理在等后台任务时结束回合，你收到的一样是 `completed`。判据是回报首行是不是它那一段该有的那个（`impl-done:` / `commit:`）——只有一句「Waiting for …」「Holding for …」就是没干完。实测一次运行里出现 5 次。

⛔ **这一类停滞的根因是异步派发**：父代理把子代理丢后台之后无事可做，只能烧回合空等。实测 157/311 次派发跑在后台、随后产生 422 个纯空转回合。**派子代理一律 `run_in_background: false`**——这条比事后救援有效得多。

- **先取状态再决定**：看宿主任务列表里该子代理是 `running`（含「停在等待」）还是 `failed`——通知文案里的 `completed` 两种情况都会给，**不能当判据**；判据是「任务状态 + 回报首行是不是它那一段该有的那个」。
  - **宿主没给你列任务的工具时**（这很常见，别因此卡住）：判据退回两条物理信号——`worktree.cjs status <flow_id>` 的**静默**列（≥30 分钟无任何文件变化 = 已停），以及一条 SendMessage 探针无回应。两者都不依赖它的自我报告。
- ⚠️ **`/clear` 不会杀掉在飞子代理**。重入相位表里「票上有 `impl:done`、工作树有未提交改动」那一行，别默认「上一轮那个已经死了」——实测 /clear 之后原子代理仍然跑完并回报，而主 session 已经为同一票另派了一个，于是两个 agent 同时写一棵车道树（一边提交、一边 `git reset` 撤回继续跑，来回三轮）。**续派之前先看宿主任务列表里那个 agent 还在不在**；不确定就在续派 prompt 里写明「可能有另一个 agent 仍在这棵树上，发现工作树被别人改动时停下回报，不要对抗性地 reset」。
- **`running` → 用 SendMessage 续派同一个**，别派新的：它带着全部上下文，重派等于让新代理从头读一遍。实测四次都是这么救回来的。**宿主不提供 SendMessage 时**：按下面那套派新代理，但 prompt 里额外写死「原代理可能仍在跑，**不要动工作树里已有的改动**，只补做契约剩余步骤」。
- **原代理已 `failed`（宿主看门狗判 stalled）→ 才派新的**，并在 prompt 里写死两条：**保留工作树现有改动、不重做实现**；**只走完契约剩余步骤**——⚠️ **按票面上有没有 `impl:done`、或分支上有没有 `[partial]` commit 选契约**：只有 `impl:done` → 按 `quality-chain.md` 派质量链（形态甲）；有 `[partial]` commit → **先按 `per-ticket-review.md` 续派实施代理做剩余清单**（那一轮不再 commit），它交付后才轮到质量链（形态乙，末尾 `--amend` 折回）；两者都无 → 实现还没做完，按 `per-ticket-review.md` 续实施段，**不要跳过实现直接评审半成品**。
- **派新代理之前先自己进树摸一遍现状**（`git -C <WT> status --porcelain`、跑一次 typecheck 与该票范围的测试），把结论写进 prompt。省掉的是新代理重新探明现状的那一轮，也避免它误判成「树是坏的」而 reset 掉一棵好树。
- **两种情形都要求它给长跑命令设超时**，否则会重蹈同一条路。优先用宿主 Bash 工具自带的 timeout 参数；用 shell 的 `timeout 900 …` 之前先确认它存在（macOS 默认没有 `timeout(1)`，需 coreutils 或 `gtimeout`——不确认就照抄会拿到 exit 127，最坏被当成测试失败去读代码）。
