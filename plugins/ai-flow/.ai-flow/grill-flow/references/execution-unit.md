# 执行单位：一票一树，还是一组一车道

> **触发**：stage-3 开工时选一次（落 `base_sha_code` 之后、开第一棵树之前）。读者是主 session。
> `<FD>` = 本文件所在目录的上一级（定义层，随插件走：`stages/` `references/` `scripts/` 都在这儿）；`<FR>` = 项目里的 `.ai-flow/<flow>`（state 在这儿）。两个都给**绝对路径**：主 session 从 stage 提示词 `[ai-flow:paths]` 块的 `flow_def:` / `flow_root:` 行取；子代理用主 session 在派发 prompt 里给的那个。

默认**一票一树**（stage-3 主循环写的就是它）。当「开树」本身成为主要成本时改成**一组一车道**：每组各开一棵长驻 worktree（名字 `R<n>`），组内逐票 commit、逐票 `close --keep` 回合，组间并行。

**选了车道模式 → 接着读 `lane-mode.md`**，它列全了动作差异和三条必须接受的代价；不读就跑，机器门⑦ 的替代保护会静默缺席。

## 怎么选：算，不要凭感觉

```sh
node <FD>/scripts/schedule.cjs --flow-dir <FR>
```

它按主循环的同一套准入算法模拟一遍，输出三个数字——墙钟下限（最长依赖链）、一票一树在各上限下的轮数、一组一车道的轮数——并给出结论。**照它的结论走**；轮数相同时选一票一树（它多一条机器门⑦）。

**为什么必须算**（下面这两条曾经是本节的主观判据，都会把人引向错误答案）：

- **「装依赖贵不贵」不是判据**。实测 pnpm store 命中时一次 19 秒，44 票一票一树也就十几分钟、还是分散在各轮里并行付的，根本不是瓶颈。真要压它，`open` 支持 `--install "<cmd>"` 覆盖探测结果（换成复用主树已有产物的命令）；但共享依赖目录会让改依赖版本的票污染别的树，只在本期没有票碰依赖清单时可用。
- **「组内是不是高度串行」也不是判据**。决定一票一树能并到多少的不是 `Blocked by`，而是 **`Touches` 相交**：两票只要写集相交就不能同批，哪怕彼此毫无依赖。实测一份 44 票的 tickets.md：上限放到 44（等于不限）仍是 18 轮，因为写集重叠把它们摊开了；而按模块分四条车道只要 14 轮——车道把「写集相交但同属一个模块」的票放进同一棵树**顺序**做（前一票的改动已经在树里，不构成冲突），于是它反而更快。**「组内串行」看着像浪费，实际那些票在一票一树下也并不起来。**

`schedule.cjs` 的输出里有一条要特别看：**放开上限到票数总量后轮数还是不降** = 瓶颈是写集相交、不是并行度。
⛔ **但这个信号不能推出「车道模式能赢」**——它只说明相交严重，没说相交是怎么分布的，而分布才决定车道模式的胜负（下一节）。
⚠️ **这一节里 18 轮 / 14 轮以及下一节的全部轮数都是 `schedule.cjs` 的模拟输出，不是跑完两种模式的墙钟实测**：
它们按同一套准入算法算「需要几轮」，可以用来横向比两种模式，不能当成小时数。

**还有一条脚本算不到、必须你自己判的**：车道数受**峰值子代理数**约束。**每票同时在跑的只有 1 个**——实施 / 质量链 / 注释清理三段是串着走的，而这三段各自都不再往下派（见下节）⇒ 峰值 ≈ 并行车道数，不是车道数 × 5。脚本说 8 条车道最快，也不代表宿主和你的额度扛得住 8 条。

## 汇聚点：轮数压不下去的那种相交，换执行单位和放宽准入都不解决

**识别信号（一眼可见）**：`schedule.cjs` 报的**连通分量数远小于票数**，且最大分量吃掉了绝大多数票。
它的成因是**一个文件被大量票同时声明**——启动装配表、注册表、导出清单、命令名清单这类「N 张
互不相干的票各追加一条」的文件。

**⛔ 这恰好是车道模式最不能赢的情形，别按上一节那个信号去选它**：汇聚点让所有票两两相交
⇒ 连通分量退化成 1 个 ⇒ 一条车道装下几乎所有票 ⇒ 车道模式变成全串行。实测一份 218 票的
tickets.md（`coldBootAssembly.ts` 被 48 张票声明、被 53 笔 commit 改过）：**一票一树 cap=3
是 108 轮，一组一车道 217 轮——车道差 2 倍**。脚本现在会在这一档直接把这句话打出来。

**三条看起来该管用、实测都不管用的路**（同一份 218 票 tickets.md，cap=3，baseline 108 轮，
墙钟下限 = 最长依赖链 30 轮）：

| 做法 | 实测轮数 | 相对 baseline |
|---|---|---|
| 把那个汇聚文件从准入相交里放开（影响 50 张票） | 104 轮 | 省 3.7% |
| 放开出现频次最高的 5 个汇聚文件（影响 64 张票） | 103 轮 | 省 4.6% |
| **`Touches` 换成该票 commit 的实际改动文件**（= 声明粒度做到完美，**任何粒度类改动的上界**） | 98 轮 | 省 9.3% |

⇒ **108 轮里 30 轮是依赖链硬下限，剩下 78 轮的超出里声明粒度只解释 10 轮，其余 68 轮是票之间
真的在改同一批文件。** 所以「把 `Touches` 写细」和「放宽准入让相交票同批」都只值一位数百分比，
⛔ **不值得为它们放宽机器门⑦**（它是一票一树模式下并行安全的唯一机器防线）。

**放宽准入还有一笔容易漏的返工成本**：往同一张表追加是 rebase 冲突概率最高的形态，不是最低——
实测两票各追加到同一处，前一票 ff 进主分支后，后一票 `git rebase` 直接退出码 1。而回合是**串行**的、
主 session **不写代码**，于是每次冲突都要人进那棵 worktree 解冲突 → `rebase --continue` → **重跑客观地板**
→ `--amend` 折回本票那笔（`worktree.cjs` 的 `sync` 就是这么要求的）。省下的几个百分比很容易被这笔吃成负。

**真解是 prefactor 掉汇聚点**，而不是在流程上给它开准入口子：把「往一张中心表追加条目」改成
「每个域自带注册声明、装配层只做汇总」，相交从结构上就没了。`stage-2.md` 的 **prefactor 前置**
（要改处先重构才好改 → 排第一个 ticket）本来就是为这种情形准备的一等公民。本仓已有的成功对照是
changeset 那种形态：每次改动新建**一个新文件**而不是往一个表里追加，所以它从不产生真冲突。
代价是多一张前置票、多一轮；换掉的是后续所有票的串行。

**本期来不及 prefactor 时的正确做法**：接受串行，并把该汇聚文件写进 tickets.md 的
「已知碰撞面」段，让 stage-4 组装审逐行看它的交界面。⛔ 不要靠拆细 `Touches` 或放宽同批准入
去「解决」它——上表说明那两条各值 3.7%–9.3%，而它们换走的是机器保护。

## 并行度：一票一树的批上限 `3`

`3` 是起步值，不是测出来的最优。**再往上，串行回合段与主 session context 的增长会吃掉并行收益**——这是它不是 5 或 8 的原因。首轮跑完记一笔：省下的（N 份实施 + 质量链自审的墙上时间）vs 付出的（回合失败时的 rebase 适配 + 批次收口测试 + N 份装依赖），再调。**装依赖那一项贵到主导总账时，要调的不是这个数字而是执行单位**——回到上一节重算。

算成本时的**实际峰值并发：每票 1 个**（实施 / 质量链 / 注释清理三段串着走，每段各自禁止往下派）⇒ 峰值 = 并行票数。

⚠️ **这一节曾按「每票 = 1 实施 + 3 评审 + `comment` skill 自己的 fan-out、3 票同时走峰值可达数十个 agent」算，那个模型已作废**：三评审改成质量链代理内部顺序自审、**`/simplify` 已整步删除**（它那四类并入 Standards 轴）、注释清理上收主 session 且承接代理禁止 fan-out（三条都在 `quality-chain.md`）。⛔ **别拿旧模型那个峰值去压车道数**——它会让你按数十个 agent 的假峰值把车道砍到跑不满。

⚠️ **真正绑住并发的不再是宿主的并发上限，而是账户额度**：实测一次同时派出的三个 `opus` 被 `individual spend limit` 全部杀掉、回报全空零产出（2026-08-31）。模型分层见 `per-ticket-review.md`——stage-3 已经没有一处该派 `opus`。

⛔ **另一条仍然成立的教训：不要 `find` / `Read` 插件目录下任何 skill 的 `SKILL.md`**（取当前版只有一种取法：用 `Skill` 工具调它——注释清理那个是 `skill: "ai-flow:comment"`，宿主注入的就是生效版本）。本机并存十几个版本目录，实测 `find` 的返回里当前版排第 2、五天前的旧版排第 7，挑中的是第 7 个，于是照着它已废弃的「一文件一子代理」派发：262 个文件的清单只跑完最重的 10 个就花掉 32M，**平均 30 个回合/文件**，而当前版的批处理在同仓是 3.7 个。⚠️ 别拿每文件单价横向比——那 10 个是按注释体量降序挑的，平均 228 行注释，批处理那组平均 30 行，**难度差 7.7 倍**；归一到「每行注释」后逐文件派发只贵 1.3–1.7 倍。**教训是版本读错，不是倍数大小。**
