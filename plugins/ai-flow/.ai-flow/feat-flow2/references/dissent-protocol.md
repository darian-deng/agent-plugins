# 用户反对意见处理协议

适用于含 Gate 的 stage（Stage 1 / 2 / 3 / 5）当用户对 AI 产出提出异议时。

## 核心纪律

用户对 AI 产出有异议时**不允许反射性接受**。"You're absolutely right"、立即改、表演性同意——都是失败模式。

按下列流程：

## 步骤 1：识别异议类型

| 类型 | 描述 |
|------|------|
| A | 用户指出 AI 没考虑到的事实约束（如「项目已废弃 X 模式」） |
| B | 用户给不同偏好但没说理由（如「换种写法」） |
| C | 用户的反对与 design.md 已有决策冲突 |
| D | 用户的反对推翻了前置 stage 已对齐的结论 |

## 步骤 2：严谨评估

- **A → 接受**，并检查 design.md 是否需要同步更新（事实约束未记录 → 立即补）
- **B → 不接受**。明确询问用户：「请给真实考量（如时间约束 / 历史经验 / 已知风险）。『感觉更好』类无信息量回应不接受。」
- **C → 与用户逐项过现有决策**。改前置决策必须先更新 design.md 含新理由，然后回流到当前 stage
- **D → 同 C**。改 design.md 是前置动作

## 步骤 3：上游影响检查

任何被驳回的 AI 结论 → 完成本 stage 修订前必须检查：

- design.md「决策记录」是否需新增、修改、删除？
- design.md「UI 设计与状态清单」是否受影响？
- design.md「验收标准」是否需调整？

发现需要 → **先更新 design.md → 再继续本 stage 修订**。

## 关键纪律

**不允许出现「本 stage 产物反映新决策，design.md 还停留旧决策」的分裂状态**——这会让 /clear 后任何 subagent 拿到分裂的 source of truth，做出不一致的实现。
