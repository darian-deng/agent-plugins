# 项目知识维护的候选规则

状态：按用户已确认目标提出的规则，尚未通过最终对抗审查或获实施批准。
范围：本次需求相关的项目规则、路径规则、项目 skills、ADR 及其语义邻居。
不做全仓重建，不改全局用户配置，不换项目知识体系。

## 维护目标

让未来没有本次会话记忆的 AI 少犯可指认的项目错误，同时减少重复、过期、过宽的指导。
不能证明“不加未来一定犯错”；新增者必须举出具体错误场景和依据，无法举证就不新增。
本次维护与代码同一个 PR；有长期知识变更才进行独立审查和额外人工批准。

## 一、先判断值不值得存在，再判断放哪里

按下列次序执行，不能靠“能找到一层放进去”证明必要性：

1. 写出触发场景、没有该指导时的具体错误、代码/实测/已批准决策证据。
2. 核实这是否为未来还会出现的项目问题。一般最佳实践、一次性调试、临时操作记录不进入长期知识。
3. 核实相关代码、类型、注释、配置或现有知识是否已足够说明/阻止该错误。已足够则不再复制；必要指针不等于复制全文。
4. 选择最便宜且可靠的表达：实现/类型/自动检查能防错，优先考虑它们；贴近单处代码的解释优先注释；只有仍有缺口才考虑 context。
5. 新增检查本身也必须属于批准范围。不能因为建议可写成 lint 就顺手扩大工程范围。声称检查能防错时，需要真实触发过反例；无法验证不能假报已完成。

## 二、先改已有，再考虑新增

每个候选只有一个主要处置结果：不写、合并到已有、修订已有、删除已失效、确有必要才新增。

- 查同一语义的既有指导，不只查关键词；沿本次相关条目的引用追踪，不扩成全项目体检。
- 相同意思只留一个权威位置。调用方可保留精确触发指针，不再抄一遍内容。
- 优先编辑已有领域文件的相关章节；不按需求 ID 建永久 rules 文件。
- 新知识和旧指导矛盾时，不默认新实现更正确；展示旧指导、代码证据、批准的决策，必要时让用户裁决。
- 无法确定适用范围时不默认放到根，也不为了少加载擅自缩窄旧规则范围。

## 三、各层职责与固定写法

不强制迁移现有目录或批量改格式。增改条目复用目标文件的既有结构；新文件才按项目约定使用下表最小形式。

| 去向 | 放什么 | 最小内容 |
|---|---|---|
| 根项目指导 | 真正全项目、每次工作都适用的约束 | 一条明确行为；必要时附简短原因/替代做法 |
| 路径规则 | 能由文件范围识别、且该范围内确实需要的知识 | 准确 paths；触发场景；行为/约束及必要例外 |
| 项目 skill | 由意图识别、有顺序意义的重复操作 | 精确触发条件、步骤、完成判据、必要分支 |
| ADR | 对未来理解有价值的架构权衡 | 上下文、决定、后果、真实考虑过的替代及理由 |
| 代码注释 | 只解释局部代码的非显然理由 | 紧邻实现的一段原因，不复述代码 |

- 流程内术语如 T3、“见本次对话”不得进入长期指导。
- 不创建只有 frontmatter 的 skill。需要时调用合适的 skill 创建/修改方法，完成正文并验证触发与步骤；不造新的空壳任务交给用户补。
- 不规定“非要反行业惯例才值得 ADR”。是否记录看长期权衡价值，不用风格偏离作必要条件。
- 不照搬 15 词/200 行等未经项目论证的硬门。不为通过计数而搬文件、删原因或新增一层参考；维护重点是有效内容与实际加载范围。
- 证据长日志、候选拒绝理由和维护过程留在 flow 记录及 PR 中，不塞进每次加载的规则正文。

## 四、改旧知识与删旧知识

新增与删除都有举证责任，但证据不同：

- 改：实现/约定已经有经过批准的改变，或可核验事实证明现有描述错误；同步修订相关示例与指针。
- 删：触发场景已消失，或已有经过验证的机制完整替代，或同语义权威来源已接管；检查依赖它的指针。
- 不足以单独判删：文件改名、搜索没命中、行数过多、模型没看懂、没有近期出错记录。
- 事故驱动指导默认保护；先核实事故机制仍可能发生否。所谓“代码里已经能推断”不是删掉一条已知防复发规则的充分理由。
- 旧 ADR 的决定失效时，按项目现有方式修订或标明失效/替代，不让旧决定继续作为当前指令；不要为本流程新造归档平台。

## 五、独立审查与人的批准

仅当长期知识 diff 非空时触发本检查，不为“无需更新”派固定额外代理。

审查者与作者分离；读取实际知识 diff、相关代码和实施前的旧指导，逐项检查：

- 有具体防错价值和可靠证据吗？
- 是否把临时绕路、测试夹具、单个模块现象泛化成全项目规范？
- 是否原本可以不写、合并或删旧，作者却选择追加？
- 是否同时修改代码和标准，给未经批准的设计变化洗白？
- scope/触发是否准确，是否有重复来源和失效指针？
- 新 skill 是否真的有正文和可执行步骤？

这是风险降低，不是正确性证明。机器门只验证产物齐全、路径/格式、审查/批准对应的修订，不声称能自动判断“值得记住”。

向用户集中展示固定清单：动作、目标、最终知识 diff、必要性/失效依据、证据、加载范围变化。用户批准的是这份确定的 diff，而非口头上“知识维护通过”。

- 等批准期间不能悄悄改知识正文；改了就重新呈现。
- 批准后仍保持代码与指导一致；后续代码变化使指导失真时，受影响审查/批准必须重开。
- 批准记录包含知识 diff、加载范围和列明的代码证据摘要。只有这些输入变化或指导失真才重开；依赖关系不确定时保守重批，不把所有无关测试/注释修改都自动变成新人工门。
- 用户拒绝可选新增：删掉该新增即可继续。
- 用户拒绝修正已被本次代码改变的旧指导：回到冲突处理，调整代码或取得新的明确决定，不能带着已知互相矛盾的指导交付。

## 六、执行完成的判据

对相关范围已经做出一个可核对结果：无需维护，或所有增改删已完成审查并由人批准。
不要求每次产出独立长总结、固定数量候选、固定数量新规则，或达到任意“知识分数”。
