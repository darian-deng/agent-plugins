# omp-feat-flow 开工审阅包

你现在审阅的是**实施计划和测试许可**，不是已经实现的插件，也不是发布批准。

## 要交付什么

一个普通开发者可 user-scope 安装的 OMP 插件，放在公开仓库
`darian-deng/agent-plugins`。入口为 `/feat-flow-start`，另外五个程序命令是
status、approve、sync、update、finish，均使用 `feat-flow-` 前缀。

有 Linear/PRD 和只有当前讨论这两个入口，都覆盖完整需求边界。已有可靠回答不重问，
但 AI 不能自行宣布讨论完成并取得写权限。产品只有对齐、实施、交付三个权限阶段；
需求复杂度影响实际活动和任务拆分，不增加固定大小分类器或固定多 stage。

每个需求一个 worktree、分支、Linear 单和 PR。项目起点、PR 目标、团队及状态映射
结构化保存；并发需求不共享 owner、当前 SHA 或批准。中途与 PR 前 sync 推进当前
审查基线，但不改起始 SHA；受影响的验证和独立审查要重做。

自动 compact、主动 compact、真实 `/clear`、新会话／同 cwd 新进程分别验收：
**第一次恢复后的实际业务请求**拿到当前阶段、批准范围、任务、未决事项和材料入口；
开发者看到据实生成的接续回执；材料或归属有问题时，实际受控写入必须被拦截。
只看源码、后来的 status 或 AI 说“恢复了”都不算通过。

## 这次需要你确认的测试接口

测试只穿过下面的公开 seams，不测试私有方法或 JSON 布局。完整计划逐项写明了能证明
什么、不能证明什么；前五类沿用既定外部测试面，最后两项是明确新增的提议。

| Seam | 实际测试面 |
|---|---|
| S1 | 真实 OMP RPC、程序命令、原生工具准入与请求上下文。 |
| S2 | Git 模块 `prepare`／`sync`／`inspectCleanup`，使用真实临时仓库和文件。 |
| S3 | 原生 OMP TUI 与 cmux 的真实键盘、字段、group/workspace、clear 和回执。 |
| S4 | 原生插件安装、user-scope 发现、升级、重装、reload 与 restart。 |
| S5 | 专用真实 GitHub PR／Linear 单、部分成功修复及实际清理。 |
| **S6 新增** | 生产控制器也调用的 Run 模块 `openRun`／`inspect`／`apply`／`admit`，用真实双进程 OS 锁测试竞争和迟到结果。它不能替代原生时序验收。 |
| **S7 新增** | 仅测试使用的本机透明计量代理，把请求原样转给已批准真实模型服务，再转回真实响应；限制请求数和输出并核对实际请求。它不是返回固定答案的 fake provider。 |

S7 不更换模型身份、原生传输实现或实际上游，不复制私有凭据库，不记录密钥，不改你的
全局模型配置。它只在测试 fixture 内用公开模型配置接入。所有推理路径不能被计量或
在发出前拒绝，就不开跑，不能只统计主会话而漏掉冷读、审查或压缩调用。

真实模型会收到合成需求／代码、原生系统与方法提示词、必要工具结果，以及可能含测试
资源 ID、操作者／团队标识的元数据；不会使用 Plaud Web 产品代码／PRD、客户资料或
密钥作为 fixture。模型服务按其自身政策留存，插件不能删除服务端数据或保证零留存。
计量器只在内存处理完整载荷，不保存认证头、完整请求或响应；保留哈希、时序／状态、
选定的合成上下文字段和脱敏结果用于核验。campaign 结束后清理临时原生配置／会话
原始日志；最小脱敏证据在私有执行索引中保留，直到你明确归档／删除。无法排除真实
生产上下文混入，就阻断测试，不转发。

## 建议怎么实施

建议在**新的原生实施会话**里由一个写手串行执行：一个行为 RED → 最小 GREEN，
每个有意义的切片后独立对照规格与规范审查，最终整体验收。不启动并行写手；新上下文
和多 agent 本身不是正确性保证。若你偏好每任务换一个全新写手，也可以明确选择串行
交接方式，而不是让多个写手同时改代码。

核心外部方法是 grilling、tdd、code-review；另九项仅在确有对应活动时采用。
依赖检查会核对新版本，但只更新此前获准、来源可核对且未被本地修改的选定副本；
进行中的 run 沿用自己的实际方法快照。不会重新强推 grill-with-docs 或一套新 docs。

发布设计不复制旧 ai-flow 的机器人提交产物模式：生成的运行包与源码随将来获准的 PR
一起提交，CI 只重建核对。新 OMP catalog 只列新插件；OMP 此后优先读它，旧 Claude
插件不因此被卸载，但不能再声称它们仍在这个新 OMP catalog 中可发现。

## 你现在可以分别授权什么

**A．计划与本地实施：**确认完整计划和 S1–S7 的接口设计；允许写产品代码和已确认
seam 的本地测试、安装开发依赖、在临时 Git/双进程中做 RED → GREEN。临时 Git
fixture 必要的提交包含在 A 内，产品仓库提交不包含。保留单写手、独立审查和整体验收。

**B．本次有界真实验收：**沿用已有测试资源类别许可，在 A 之外确认本次实际开跑时机、
新增 S7 接入及下列上限；不是重问 Desktop 归属。范围包括专用原生配置的安装／升级／
重启、自建 cmux 临时资源、专用私有 GitHub 测试仓库／PR、新的 Desktop 非 Bug 测试单。
创建专用仓库和 Linear 测试单前核验删除权限；测后关闭 owned PR、删除 owned 专用仓库
及 Linear 单（Linear 进入 30 天回收期，平台保留政策仍适用）。任何 owned 资源清理失败
都不能报告全流程通过。不触碰正式需求单和现有产品／Bug 对象，不改全局登录状态。

B 的真实模型提议固定为 `llm-proxy-v2/kimi-k3.1-pro`。一次 campaign 最多 **96 次实际
转发推理请求**；每请求核对 **8192 输出 token 上限参数、1 MiB 请求体上限**。单场景
串行且最多 **5 分钟 wall-clock**，全部真实测试累计活跃时长最多 **30 分钟**；修代码
的间隔不计，运行中的场景不能暂停计时。重试、辅助 agent、压缩和标题调用都计入，
触顶失败，只继续无推理的可达清理，不追加。模型不可用或不支持限额就阻断，不偷换
模型。这是请求／时间限制，不是实际账单担保。
本次 B 只授权**一个 campaign**，包含其 RED／GREEN／整合重跑；不得另起进程或
campaign 重置额度，任何追加均须重新明确批准。上述限额只针对被测插件的真实验收，
不包含开发会话本身及其独立开发审阅调用。

A 和 B 都**不包含产品仓库的 commit／push／PR、合并、发布或生产配置安装**。
远端专用测试仓库的临时提交／push／PR 仅属于你选择的 B；与产品仓库操作分开。
